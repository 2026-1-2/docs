## Question
```
MediaMTX 는 동시에 여러 스트림 변환을 지원하나?
```
## Answer
**MediaMTX**는 여러 스트림의 **동시 변환(Conversion) 및 배포를 지원**합니다. 다만, '변환'의 의미를 **프로토콜 전환**과 **트랜스코딩(인코딩)**으로 구분해서 이해하는 것이 중요합니다.

---

## 1. 프로토콜 변환 (Protocol Conversion)
MediaMTX는 기본적으로 **미디어 브로커** 역할을 수행하며, 다음과 같은 프로토콜 간의 전환을 **추가 설정 없이 동시에** 처리합니다.
*   **지원 프로토콜:** RTSP, RTMP, HLS, WebRTC, SRT 등.
*   **동작 방식:** 하나의 RTSP 스트림이 들어오면, 서버는 이를 내부적으로 인지하여 사용자가 요청하는 방식(예: HLS나 WebRTC)으로 실시간 변환하여 내보냅니다. 이 과정은 여러 스트림에 대해 동시에 병렬로 수행됩니다.

## 2. 트랜스코딩 (Transcoding/Encoding)
해상도를 변경하거나(1080p → 720p), 코덱을 바꾸는(H.264 → H.265) 등의 **재인코딩** 작업은 MediaMTX가 직접 수행하지 않고 외부 도구인 **FFmpeg**를 호출하여 처리합니다.

### 동시 변환 구현 방법
`mediamtx.yml` 설정 파일의 `paths` 섹션에서 각 스트림별로 독립적인 변환 규칙을 정의할 수 있습니다.

*   **`runOnReady` 이용:** 특정 경로에 스트림이 입력되었을 때 FFmpeg를 실행하여 여러 버전으로 변환합니다.
    ```yaml
    paths:
      original_stream:
        # 스트림이 들어오면 실행
        runOnReady: ffmpeg -i rtsp://localhost:$RTSP_PORT/$RTSP_PATH 
                    -c:v libx264 -s 1280x720 -f rtsp rtsp://localhost:$RTSP_PORT/720p_stream
                    -c:v libx264 -s 640x360 -f rtsp rtsp://localhost:$RTSP_PORT/360p_stream
    ```
*   **다중 경로(Multi-path):** 여러 대의 CCTV나 소스 기기가 각각 다른 경로(`path1`, `path2` 등)로 데이터를 보내면, MediaMTX는 이를 각각의 프로세스로 관리하여 동시에 처리합니다.



## 3. 성능 및 제약 사항
*   **CPU/GPU 부하:** MediaMTX 자체는 Go 언어로 작성되어 가볍고 동시성 처리에 능하지만, **변환(Transcoding)** 작업은 FFmpeg의 성능에 의존합니다. 동시에 많은 스트림을 변환하려면 CPU 자원이 많이 소모되므로, 하드웨어 가속(NVENC, VAAPI 등)을 활용해야 합니다.
*   **동시성:** 수백 개의 동시 접속(Reading)을 처리하는 데 최적화되어 있으나, '변환' 프로세스가 많아질수록 시스템의 I/O와 연산 능력이 병목 지점이 됩니다.

### 요약
*   **동시 프로토콜 전환:** 기본 지원 (매우 가벼움).
*   **동시 트랜스코딩:** FFmpeg 연동을 통해 지원 (시스템 자원 소모가 큼).
*   **관리 방식:** 설정 파일의 `paths`에서 개별적으로 제어 가능.

현재 진행 중인 CCTV 녹화 및 제어 서버 프로젝트에서 여러 채널의 해상도를 낮추어 모니터링하거나 저장해야 한다면, 위와 같이 `runOnReady`와 FFmpeg 하드웨어 가속을 조합하여 구성하는 것이 가장 효율적입니다.

## 2. 우분투 기본 설치 및 실행 순서

### ① 바이너리 다운로드 및 압축 해제
[Releases](https://github.com/bluenviron/mediamtx/releases) 페이지에서 우분투 환경(보통 `linux_amd64.tar.gz`)에 맞는 최신 버전을 받습니다.

```bash
# 다운로드 (버전 숫자는 최신으로 변경 가능)
wget https://github.com/bluenviron/mediamtx/releases/download/v1.9.0/mediamtx_v1.9.0_linux_amd64.tar.gz

# 압축 해제
tar -xvzf mediamtx_v1.9.0_linux_amd64.tar.gz
```

### ② 설정 파일(`mediamtx.yml`) 수정
WebRTC를 사용하기 위해 최소한의 설정을 확인합니다. 기본적으로 WebRTC는 활성화되어 있지만, 외부 접속 환경(NAT 등)에 있다면 추가 설정이 필요할 수 있습니다.

```yaml
# mediamtx.yml 주요 부분
paths:
  # 'cam1'이라는 경로로 들어오는 RTSP를 정의
  cam1:
    source: rtsp://[카메라_IP]:554/stream_path

# WebRTC 관련 설정 섹션
webrtc: yes
webrtcAddress: :8889
webrtcICEUDP: yes
# 서버가 공인 IP 뒤에 있다면 해당 IP를 적어줘야 원활한 통신이 가능합니다.
# webrtcICEUDPMuxAddress: :8189 
```

### ③ 서비스 등록 (선택 사항)
서버 재부팅 시에도 자동으로 실행되도록 `systemd`에 등록하는 것이 좋습니다.

```bash
sudo cp mediamtx /usr/local/bin/
sudo cp mediamtx.yml /usr/local/etc/

# 서비스 파일 생성 (/etc/systemd/system/mediamtx.service)
# 내용을 채운 후 아래 명령어 실행
sudo systemctl enable mediamtx
sudo systemctl start mediamtx
```

## 3. WebRTC 병렬 처리 확인 방법


1.  **스트림 입력:** 여러 대의 CCTV가 각각 다른 `path`(`cam1`, `cam2`, `cam3`...)로 스트림을 보냅니다.
2.  **변환 및 배포:** 클라이언트가 웹 브라우저에서 `http://[서버IP]:8889/cam1` 등으로 접속하면, MediaMTX는 각 경로에 대해 독립적인 WebRTC 세션을 즉시 생성하여 병렬로 처리합니다.
3.  **포트 주의:** WebRTC는 데이터 전송을 위해 UDP 포트를 사용합니다. 방화벽 설정 시 WebRTC 관련 포트(기본 8889 및 UDP 포트 범위)가 열려 있는지 확인해야 합니다.

### 팁: 하드웨어 가속
만약 단순히 프로토콜만 바꾸는 게 아니라, 웹 브라우저 호환성을 위해 **코덱 변환(H.265 → H.264)**이 동반되어야 한다면, 앞서 언급한 FFmpeg 연동 시 우분투 환경의 **VAAPI**나 **NVENC** 가속 옵션을 반드시 추가하시기 바랍니다.

현재 구축 중인 시스템에서 여러 채널을 동시에 띄울 때 지연 시간(Latency) 문제가 발생한다면, WebRTC의 `ICE 서버` 설정이나 `UDP` 전송 모드를 중점적으로 튜닝해 보시는 것을 추천합니다.

## Question
```
mediamtx.yml 파일에서 rtsp를 받아올 카메라 주소만 쓰면 되나?
어떻게 해야 하지?
```
## Answer
네, 맞습니다. `mediamtx.yml` 파일의 `paths` 섹션에 카메라의 RTSP 주소를 적어주기만 하면, MediaMTX가 해당 주소로 접속해 영상 스트림을 끌어옵니다(Proxy 또는 Pull 방식).

설정 방법은 매우 직관적입니다. 상황에 맞게 몇 가지 유용한 옵션만 추가해 주시면 됩니다.

---

### 1. 기본 설정 방법

`mediamtx.yml` 파일을 열고 하단의 `paths:` 부분을 찾아 아래와 같이 작성합니다.

```yaml
paths:
  # 'cam1'이라는 이름의 스트림 경로 생성
  cam1:
    # 카메라의 RTSP 주소 입력 (아이디와 비밀번호 포함)
    source: rtsp://admin:password123@192.168.1.100:554/stream1

  # 여러 대일 경우 아래에 계속 추가
  cam2:
    source: rtsp://admin:password123@192.168.1.101:554/profile2
```
* **형식:** `rtsp://[아이디]:[비밀번호]@[카메라IP]:[포트]/[스트림경로]`
* **주의:** 특수문자가 비밀번호에 포함되어 있다면 URL 인코딩(예: `@`는 `%40`)을 해야 할 수도 있습니다.

---

### 2. CCTV 환경을 위한 필수 추가 옵션

단순히 주소만 적어도 동작하지만, 안정적인 운영을 위해 카메라 설정 하단에 다음 두 가지 옵션을 추가하는 것을 권장합니다.

```yaml
paths:
  cam1:
    source: rtsp://admin:password123@192.168.1.100:554/stream1
    sourceProtocol: tcp
    sourceOnDemand: yes
```

*   **`sourceProtocol: tcp`**
    *   **이유:** RTSP는 기본적으로 UDP를 사용하지만, 네트워크 패킷이 유실되면 화면이 깨지거나 회색으로 번지는 현상(Smearing)이 발생합니다. 이를 `tcp`로 명시하면 패킷 유실을 방지하여 훨씬 안정적인 영상을 얻을 수 있습니다.
*   **`sourceOnDemand: yes`** (또는 `no`)
    *   **`yes`:** 클라이언트(웹 브라우저 등)가 접속해서 영상을 요청할 때만 카메라에 연결하여 스트림을 가져옵니다. 접속자가 없으면 연결을 끊어 대역폭과 서버 자원을 아낍니다.
    *   **`no` (기본값):** 서버가 켜져 있는 내내 카메라와 연결을 유지합니다. 상시 녹화를 병행해야 한다면 `no`로 설정해야 합니다.

### 3. 설정 완료 후 WebRTC로 확인하기

설정 파일을 저장하고 MediaMTX를 실행(또는 재시작)합니다.

별도의 웹 서버를 구축하지 않아도, MediaMTX가 자체적으로 제공하는 WebRTC 테스트 페이지를 통해 즉시 병렬 출력을 확인할 수 있습니다.

웹 브라우저를 열고 다음 주소로 접속합니다:
*   `http://[우분투서버_IP]:8889/cam1`
*   `http://[우분투서버_IP]:8889/cam2`

해당 주소로 들어가면 브라우저에 바로 WebRTC 기반의 지연 없는 실시간 영상이 출력됩니다. 여러 탭이나 여러 기기에서 동시에 접속해도, MediaMTX가 내부적으로 병렬 처리하여 화면을 뿌려주게 됩니다.

파이썬으로 rtsp -> webRTC 변환하는 것과 mediaMTX 를 사용하는 것 중, 뭐가 더 효율적이지?
```
## Answer
결론부터 말씀드리면, **대규모 배포나 안정적인 운영이 목적이라면 MediaMTX를 사용하는 것이 압도적으로 효율적**입니다. 

하지만 특정 상황(실시간 AI 분석 등)에 따라 파이썬이 유리할 때도 있습니다. 두 방식의 핵심 차이를 정리해 드립니다.

---

### 1. 효율성 비교: MediaMTX vs. Python (aiortc 등)

| 비교 항목 | MediaMTX (Go 기반) | Python (aiortc/OpenCV) |
| :--- | :--- | :--- |
| **성능 (I/O)** | **매우 높음.** 고성능 비동기 I/O와 Go의 고루틴을 활용해 수백 개의 스트림을 병렬 처리하는 데 최적화되어 있습니다. | **보통.** 파이썬의 GIL(Global Interpreter Lock)과 비동기 처리 한계로 인해 스트림 수가 늘어날수록 CPU 부하가 급증합니다. |
| **개발 속도** | **즉시 가능.** `yml` 설정 파일 수정만으로 RTSP -> WebRTC 변환이 즉시 완료됩니다. | **느림.** WebRTC의 복잡한 시그널링(SDP 교환), ICE candidate 처리, 네트워크 소켓 로직을 직접 구현해야 합니다. |
| **안정성** | **매우 높음.** 다양한 네트워크 환경(NAT, 방화벽)에 대응하는 로직이 이미 검증되어 있습니다. | **낮음.** 네트워크 단절 시 재연결 로직, 메모리 관리 등을 직접 정교하게 설계해야 합니다. |
| **확장성** | RTSP 외에도 RTMP, HLS, SRT 등을 동시에 지원하며 서버 자원을 효율적으로 사용합니다. | 커스텀 로직(예: 프레임 가공)을 넣기엔 좋으나, 단순 프로토콜 변환 시에는 자원 낭비가 큽니다. |

---

### 2. 왜 MediaMTX가 더 유리한가?

1.  **프로토콜 스택의 완성도:** WebRTC는 단순히 영상을 보내는 것이 아니라, 브라우저와 복잡한 핸드셰이크 과정을 거칩니다. MediaMTX는 이를 표준에 맞춰 완벽하게 구현해 두었기 때문에 브라우저 호환성 문제가 거의 없습니다.
2.  **리소스 관리:** 파이썬은 패킷 하나하나를 객체로 처리하면서 발생하는 오버헤드가 크지만, Go 언어 기반인 MediaMTX는 시스템 자원을 적게 쓰면서도 많은 동시 접속을 버팁니다.
3.  **유지보수:** CCTV 채널이 추가될 때 파이썬 코드를 수정하고 디버깅하는 것보다, 설정 파일에 한 줄 추가하는 것이 훨씬 관리하기 쉽습니다.

---

### 3. 그럼에도 파이썬을 써야 하는 경우

만약 다음과 같은 요구사항이 있다면 파이썬 기반 구현이 고려 대상이 됩니다.

*   **실시간 영상 처리:** 스트림을 변환하는 도중에 OpenCV나 PyTorch를 사용해 **실시간 객체 탐지(Object Detection)**를 수행하고, 그 결과가 포함된 영상을 다시 송출해야 할 때.
*   **완전한 커스텀 시그널링:** 표준 방식이 아닌 독자적인 인증 방식이나 복잡한 비즈니스 로직을 스트리밍 세션에 녹여내야 할 때.

### 요약 및 제안

현재 진행 중인 **CCTV 원격 제어 및 녹화 서버 구축**이 목적이라면, **MediaMTX를 미디어 엔진(백본)**으로 사용하시길 강력히 추천합니다.

*   **영상 전송 및 변환:** MediaMTX에 맡깁니다. (RTSP -> WebRTC)
*   **제어 및 부가 기능:** 파이썬으로 API 서버를 만들어 MediaMTX의 API를 제어하거나, 카메라의 ONVIF 명령을 날리는 방식으로 역할을 분담하는 것이 가장 효율적인 아키텍처입니다.

단순히 텍스트 파일을 수정하고 서버를 재시작하는 대신, 다음과 같은 방법들을 추천합니다.

## 1. REST API를 통한 동적 관리 (가장 추천)
MediaMTX는 실행 중에 스트림 경로(paths)를 추가, 수정, 삭제할 수 있는 강력한 **REST API**를 제공합니다. 이를 활용하면 DB에 저장된 카메라 정보를 바탕으로 파이썬이 MediaMTX의 설정을 실시간으로 바꿀 수 있습니다.

### 설정 방법 (`mediamtx.yml`)
먼저 API 기능을 활성화해야 합니다.
```yaml
api: yes
apiAddress: :9997  # 기본 포트
```

### 파이썬에서의 제어 예시 (DB -> MediaMTX)
파이썬에서 DB(MySQL, PostgreSQL, SQLite 등)를 읽어 MediaMTX에 경로를 등록하는 로직을 짤 수 있습니다.

```python
import requests

# 새로운 카메라 스트림 추가 (POST 요청)
def add_camera(name, url):
    api_url = f"http://localhost:9997/v3/config/paths/add/{name}"
    payload = {
        "source": url,
        "sourceProtocol": "tcp"
    }
    response = requests.post(api_url, json=payload)
    return response.status_code

# 예: DB에서 읽어온 데이터 적용
add_camera("hallway_cam", "rtsp://admin:1234@192.168.1.50/stream")
```
*   **장점:** 서버를 재시작할 필요가 없으며, 웹 대시보드나 관리 툴에서 카메라를 추가하는 즉시 서비스에 반영됩니다.
*   **CRUD 지원:** `GET`으로 현재 목록 확인, `PATCH`로 수정, `DELETE`로 삭제가 모두 가능합니다.

---

## 2. 구성 관리 도구(Template) 방식
만약 API 방식이 번거롭고 "파일" 기반으로 관리하고 싶다면, 파이썬의 **Jinja2** 같은 템플릿 엔진을 사용하여 설정 파일을 생성하는 방식을 씁니다.

1.  `mediamtx.yml.j2` 템플릿 파일을 만듭니다.
2.  파이썬이 DB에서 카메라 리스트를 가져옵니다.
3.  템플릿에 리스트를 주입해 최종 `mediamtx.yml`을 생성합니다.
4.  MediaMTX 프로세스에 `SIGHUP` 신호를 보내거나 재시작하여 설정을 갱신합니다.

---

## 3. 환경 변수 활용
설정 파일 내에서 특정 값을 환경 변수로부터 읽어오게 할 수 있습니다. 하지만 이는 단일 값(예: 비밀번호, IP 등)에는 유용하나, 수십 대의 카메라 리스트를 동적으로 관리하기에는 부적합합니다.

## Answer
로그의 **`deadline exceeded while waiting connection`**이라는 문구는 WebRTC의 **시그널링(연결 준비)은 성공했지만, 실제 영상 데이터를 주고받는 통로(ICE/UDP)가 열리지 않아 타임아웃이 발생**했다는 뜻입니다.

쉽게 말해, 서버와 브라우저가 "우리 이제 영상 주고받자"라고 약속은 했으나, 정작 데이터가 지나갈 문(UDP 포트)을 찾지 못해 10초(기본값) 동안 기다리다가 연결을 끊어버린 상황입니다.

---

### 원인 및 해결 방법 3가지

#### 1. UDP 포트 개방 및 방화벽 확인 (가장 흔한 원인)
WebRTC는 제어용인 TCP 포트(8889) 외에 실제 데이터를 실어 나를 **UDP 포트**가 필요합니다.
*   로그를 보면 `:8189 (UDP/ICE)`가 열려 있습니다. 우분투 방화벽(`ufw`)에서 해당 포트가 열려 있는지 확인하세요.
*   **해결책:** 
    ```bash
    sudo ufw allow 8889/tcp
    sudo ufw allow 8189/udp
    ```

#### 2. 서버 IP 설정 (NAT/공유기 환경)
서버가 공유기 아래에 있거나 가상 환경(Docker, VM)에 있는 경우, 브라우저에게 "내 주소는 여기야"라고 알려주는 IP가 사설 IP(192.168.x.x)로 전달되어 외부에서 접속을 못 할 수 있습니다.

*   **해결책:** `mediamtx.yml`에서 아래 설정을 찾아 서버의 실제 IP를 명시해 보세요.
    ```yaml
    webrtcICEUDPMuxAddress: :8189
    # 만약 서버가 공인 IP를 가진다면 해당 IP를 적어주세요.
    # 예: webrtcICEUDPMuxAddress: 1.2.3.4:8189 
    ```

#### 3. 브라우저의 코덱 호환성
로그에 `1 track (H264)`라고 정상적으로 뜹니다. 대부분의 브라우저는 H.264를 지원하지만, 가끔 **H.265(HEVC)** 스트림을 WebRTC로 보낼 때 브라우저가 처리를 못 하면 검은 화면만 나올 수 있습니다. 
*   **확인법:** 카메라 설정에서 비디오 코덱이 **H.264**로 되어 있는지 확인하세요. 만약 H.265라면 앞서 말씀드린 FFmpeg를 이용한 트랜스코딩이 필요합니다.

### 빠른 디버깅 팁
1.  **브라우저 콘솔 확인:** 브라우저에서 `F12`를 눌러 **Console** 탭을 보세요. `ICE connection failed`나 `STUN` 관련 에러가 떠 있다면 100% 네트워크/방화벽 문제입니다.

### 2. 설정 파일의 들여쓰기(Indentation) 확인
제공해주신 코드 스니펫에서 **들여쓰기**가 올바른지 다시 한번 봐주세요. YAML 파일은 들여쓰기 한 칸 차이로 경로를 인식하지 못할 수 있습니다.

```yaml
# 올바른 예시
paths:
  cam1:  # 'paths'보다 두 칸 안으로
    source: rtsp://admin:cdp2-cam-small@27.35.108.50:554/Sources/Channel/101
    sourceProtocol: tcp
    sourceOnDemand: yes
```
*   만약 `cam1:` 앞에 공백이 너무 많거나 적으면 MediaMTX가 이를 경로로 인식하지 못해 404를 보낼 수 있습니다.

```yaml
webrtc: yes  # 이 부분이 'no'로 되어 있으면 해당 경로로 접속 시 404가 뜹니다.
```

### 4. 404 에러 시 MediaMTX 로그 확인
브라우저에서 접속을 시도했을 때, 우분투 터미널(MediaMTX 실행창)에 어떤 로그가 찍히나요?

*   만약 로그에 다른 이름의 경로(예: `all`, `proxied`)가 찍힌다면 주소 오타입니다.

## Answer
그 에러 메시지(`Uncaught (in promise) The message port closed before a response was received`)는 사실 **MediaMTX 자체의 결함이라기보다는 브라우저(Chrome 기반) 확장 프로그램과의 충돌**에서 발생하는 경우가 많습니다.

하지만 이 메시지가 뜬다는 것은 브라우저가 MediaMTX 서버에 접속은 시도했다는 뜻이므로, 현재 **404 에러를 해결하는 것이 최우선**입니다.

---

### 1. "Message port closed" 에러 무시하기
이 에러는 보통 크롬 확장 프로그램(AdBlock, 번역기 등)이 페이지 응답을 가로채려다 실패할 때 발생합니다. 
*   **해결책:** 브라우저의 **시크릿 모드(Ctrl+Shift+N)**를 열고 `[http://192.168.0.200:8889/cam1](http://192.168.0.200:8889/cam1)`에 접속해 보세요. 여기서도 똑같이 404가 뜨는지 확인하는 것이 중요합니다.

---

### 2. 404 에러 해결을 위한 체크리스트 (가장 유력한 원인들)

#### ① URL 끝의 슬래시(`/`) 제거 (가장 의심됨)
앞서 말씀드린 것처럼 `.../cam1/` 대신 **`.../cam1`**으로 접속해 보세요. 
*   MediaMTX는 `/cam1`을 스트림 경로로 인식하지만, 뒤에 슬래시가 붙은 `/cam1/`은 "cam1이라는 디렉토리 안의 index 파일"을 찾는 것으로 오해하여 404를 낼 수 있습니다.

#### ② `webrtc: true`를 `webrtc: yes`로 변경
YAML 파일에서 `true`도 불리언 값으로 인식되긴 하지만, MediaMTX 공식 가이드에서는 **`yes`**와 **`no`**를 표준으로 사용합니다. 사소한 파싱 오류를 방지하기 위해 아래와 같이 수정해 보세요.
```yaml
webrtc: yes
```

#### ③ 설정 파일 로드 확인 (가장 중요!)
MediaMTX가 실행될 때 터미널에 뜨는 **맨 처음 로그들**을 다시 봐주세요. 설정이 제대로 로드되었다면 반드시 아래와 같은 로그가 찍혀야 합니다.

> `[path cam1] [RTSP source] started`

만약 이 로그가 없다면, `mediamtx.yml` 파일에서 `cam1` 설정의 **들여쓰기가 잘못되어 MediaMTX가 이 경로를 아예 무시하고 있는 것**입니다.

---

### 3. 디버깅을 위한 시도

현재 설정이 올바른지 확인하기 위해, 브라우저 주소창에 아래 주소를 입력해 보세요.
*   **주소:** `[http://192.168.0.200:9997/v3/config/paths/list](http://192.168.0.200:9997/v3/config/paths/list)` (API 포트가 9997인 경우)

**결과 확인:**
*   여기에 접속했을 때 `cam1`이라는 이름이 리스트에 나오나요?
*   만약 리스트가 비어 있거나 `cam1`이 없다면, **설정 파일(`mediamtx.yml`)의 위치가 잘못되었거나 들여쓰기 오류**입니다.

### 요약 해결책
1.  **시크릿 모드**에서 접속해 본다.
2.  주소 끝의 **슬래시를 제거**한다: `[http://192.168.0.200:8889/cam1](http://192.168.0.200:8889/cam1)`

---

### 1. `mediamtx.yml` 핵심 설정 수정
WebRTC는 "나 여기 있으니 이쪽으로 영상을 보내!"라고 서로 주소를 교환(ICE)합니다. 그런데 VM 안에 있으면 서버가 자기 주소를 잘못 알려주는 경우가 많습니다.

`mediamtx.yml`에서 아래 항목들을 찾아 다음과 같이 수정해 보세요.

```yaml
# 1. WebRTC 서버의 주소를 명시적으로 지정
# VMware 가상머신의 IP인 192.168.0.200을 직접 적어줍니다.
webrtcServerIP: 192.168.0.200

# 2. UDP 포트 고정 (Muxing)
# 여러 포트를 열지 않고 8189 하나로 데이터를 주고받게 강제합니다.
webrtcICEUDPMuxAddress: :8189

# 3. (로그의 경고 해결) sourceProtocol 대신 아래 문법 권장
paths:
  test:
    source: rtsp://admin:cdp2-cam-small@27.35.108.50:554/Sources/Channel/101
    rtspTransport: tcp # sourceProtocol 대신 이것을 사용하세요.
    sourceOnDemand: yes
```

### 2. VMware 네트워크 모드 확인
VMware의 네트워크 설정이 어떻게 되어 있느냐에 따라 UDP 패킷 전송 여부가 달라집니다.

*   **NAT 모드인 경우:** 호스트 PC에서 VM 내부로 들어가는 UDP 8189 포트가 차단될 확률이 높습니다. 
    *   **해결:** VMware 설정에서 **Port Forwarding**을 통해 UDP 8189를 VM으로 넘겨주거나, 가급적 **Bridged 모드**로 변경하여 VM이 공유기로부터 직접 IP를 할당받게 하는 것이 가장 깔끔합니다.
*   **Bridged 모드인 경우:** 위 `webrtcServerIP` 설정만 제대로 하면 바로 해결될 것입니다.

### 3. 브라우저 및 방화벽 최종 점검
*   **방화벽:** 우분투 내부에서 `sudo ufw allow 8189/udp`가 확실히 되어 있는지 다시 확인해 주세요.
*   **시크릿 모드:** 브라우저 캐시나 확장 프로그램 간섭을 피하기 위해 `[http://192.168.0.200:8889/test](http://192.168.0.200:8889/test)`를 시크릿 모드 창에서 열어보세요.

---

### 왜 이 문제가 발생하나요? (기술적 배경)

WebRTC는 **Signaling(TCP 8889)**을 통해 "연결할 준비가 됐다"는 신호를 먼저 보냅니다. (그래서 로그에 `session created`는 뜨는 것입니다.) 하지만 실제 **미디어 데이터(UDP)**는 별도의 통로로 흐르는데, 이때 서버가 브라우저에게 "내 주소는 172.x.x.x(VM 내부망)야!"라고 알려주면, 호스트 PC의 브라우저는 그 주소를 찾지 못해 대기하다가 10초 뒤에 `deadline exceeded`로 끊어버리는 것입니다.

`webrtcServerIP`를 실제 호스트가 접근 가능한 `192.168.0.200`으로 고정하는 것이 이 문제의 핵심 열쇠입니다. 설정을 바꾼 후 MediaMTX를 다시 실행해 보세요!

`webrtc:` 섹션을 찾아 아래 내용을 **직접 추가**해 주셔야 합니다. (제가 앞서 말씀드린 `webrtcServerIP`는 개념적인 명칭이었으며, 실제 v1.x 버전에서 사용하는 정확한 파라미터명으로 다시 정리해 드립니다.)

### 1. `mediamtx.yml`에 추가해야 할 정확한 옵션

파일 내에서 `webrtc:` 라고 시작하는 부분을 찾으신 후, 그 바로 아래에 다음 내용을 추가(또는 수정)하세요.

```yaml
webrtc: yes
# 1. 시그널링 주소 (이미 설정되어 있을 겁니다)
webrtcAddress: :8889

# 2. ICE UDP 전송 활성화
webrtcICEUDP: yes

# 3. UDP Mux 주소 (매우 중요)
# 포트 앞에 VM의 IP인 192.168.0.200을 직접 붙여주세요. 
# 이렇게 하면 MediaMTX가 외부로 "내 주소는 여기야"라고 정확히 알립니다.
webrtcICEUDPMuxAddress: 192.168.0.200:8189

# 4. ICE 서버 설정 (NAT 환경에서 연결을 도와줍니다)
# 같은 로컬망이라도 구글 STUN 서버를 넣어주면 브라우저가 경로를 더 잘 찾습니다.
webrtcICEServerList: [stun:stun.l.google.com:19302]
```

---

### 2. 왜 옵션이 없었나요?
MediaMTX는 설정 파일이 복잡해지는 것을 막기 위해 자주 쓰이지 않는 옵션은 숨겨둡니다. 하지만 지금처럼 **VMware NAT** 환경에서는 서버가 자신의 IP를 브라우저에게 제대로 전달하지 못하는 "ICE Candidate" 문제가 발생하므로, 위와 같이 **IP를 명시적으로 적어주는 설정**이 필수적입니다.

---

### 3. VMware 환경에서의 최종 해결 로직

현재 `deadline exceeded`가 뜨는 이유는 다음과 같은 상황이기 때문입니다.
1. 브라우저(호스트)가 서버(VM)에 접속함.
2. 서버가 브라우저에게 "내 주소는 `172.x.x.x`(VM 내부망 주소)야, 이쪽으로 영상 보내!"라고 말함.
3. 호스트 브라우저는 `172.x.x.x`라는 주소를 알 길이 없어서 10초간 멍하니 기다리다 연결이 끊김.

**해결책:**
*   **방법 A (추천):** VMware 네트워크 설정을 **NAT**에서 **Bridged**로 변경하세요. 그러면 VM이 호스트와 같은 공유기 IP 대역을 할당받아 복잡한 설정 없이 바로 연결됩니다.
*   **방법 B (현재 설정 유지):** 위에서 알려드린 `webrtcICEUDPMuxAddress: 192.168.0.200:8189` 설정을 넣고 MediaMTX를 재시작하세요.

    우분투(VM) 내부에서 `8189/udp`가 열려 있는지 다시 확인합니다.
    ```bash
    sudo ufw allow 8189/udp
    ```

3.  **주소창 확인:**
    `http://192.168.0.20드디어 원인이 확실히 보입니다! 문제는 **도커 포트 포워딩 불일치**에 있습니다.

`docker ps` 결과를 보면 UDP 포트가 `8181(Host) -> 8189(Container)`로 매핑되어 있습니다. 하지만 MediaMTX 내부 로그에서는 `8189` 포트에서 리스너가 열렸다고 나옵니다. 이 경우 WebRTC 연결이 실패하는 이유는 다음과 같습니다.

1.  **신호 전달:** 브라우저가 TCP 8889를 통해 서버에 접속합니다.
2.  **포트 약속:** MediaMTX는 브라우저에게 "내 **8189** 포트로 영상 데이터를 보내줘!"라고 말합니다. (컨테이너 내부 포트 기준)
3.  **데이터 전송 실패:** 브라우저(호스트 PC)는 `192.168.0.200:8189`로 UDP 패킷을 보냅니다. 하지만 도커 호스트는 **8181** 포트만 열어두었기 때문에, **8189**로 들어오는 패킷은 증발해 버립니다.

---

### 해결 방법: 포트 번호를 1:1로 일치시키기

WebRTC는 내부적으로 포트 번호를 시그널링 데이터(SDP)에 담아 보내기 때문에, 가급적 **호스트와 컨테이너의 포트 번호를 동일하게 맞추는 것**이 정신 건강에 이롭습니다.

#### 방법 1. 도커 실행 옵션 수정 (추천)
호스트 포트를 `8181`이 아닌 `8189`로 변경하여 다시 실행하세요.
```bash
# 기존 컨테이너 중지 및 삭제 후 실행
docker run --rm -it \
  -p 8889:8889 \
  -p 8189:8189/udp \
  -v $(pwd)/mediamtx.yml:/mediamtx.yml \
  mediamtx:latest
```

#### 방법 2. `mediamtx.yml`에서 외부 포트 알려주기
만약 반드시 호스트 포트를 `8181`로 써야 한다면, MediaMTX에게 "외부에서는 8181로 접속해야 해"라고 알려줘야 하지만, MediaMTX v1.x 버전에서는 UDP Muxer의 포트를 외부와 다르게 설정하는 것이 까다롭습니다. 따라서 **방법 1**을 강력히 권장합니다.

### 최종 점검 리스트

포트를 `8189:8189/udp`로 맞춘 후에도 안 된다면 다음 설정을 다시 확인해 주세요.

1.  **`mediamtx.yml` 수정:**

    ```

3.  **주소창 확인:**
    `http://192.168.0.200:8889/test` (끝에 `/` 없이 접속)



**요약:** 현재 `docker ps` 상의 `8181 -> 8189` 매핑이 `deadline exceeded`를 유발하는 주범입니다. 이를 `8189 -> 8189`로 바꾸면 브라우저가 보낸 영상 데이터 패킷이 정확히 컨테이너 내부로 배달될 것입니다.

## Question
```
webRTC 주소를 바로 받을 수 없나?
```
## Answer
```
이 방식은 MediaMTX가 복잡한 WebRTC 연결 로직을 다 처리해주기 때문에, 개발자는 주소만 갖다 쓰면 됩니다.

---

### 왜 RTSP처럼 `webrtc://...` 식의 주소가 없나요?

WebRTC는 연결을 맺기 위해 **SDP(Session Description Protocol)**라는 텍스트 데이터를 주고받아야 합니다. 이 과정이 마치 전화 통화를 연결하는 것과 비슷해서, 단순히 "주소"만으로는 통화(영상 전송)를 시작할 수 없습니다.



---

### 실전 팁: 다른 프로그램에서 이 영상을 받고 싶다면?

1.  **웹 브라우저가 아닌 곳에서 받을 때:** WHEP를 지원하는 라이브러리나 소프트웨어를 써야 합니다.
2.  **API로 주소 목록을 관리할 때:** 이전에 말씀드린 REST API(`:9997`)를 통해 현재 활성화된 모든 경로의 리스트를 JSON으로 받아와서 프론트엔드에 뿌려줄 수 있습니다.

### 마지막으로 포트 점검!
지금 계속 `deadline exceeded` 에러가 나고 있다면, 주소를 어떻게 받든 영상은 나오지 않습니다. 이전 답변에서 말씀드린 **포트 매핑(`8189:8189/udp`)**을 먼저 맞춘 뒤에, `http://192.168.0.200:8889/test` 주소를 활용하시기 바랍니다.

혹시 이 주소를 어디(예: 자체 제작 웹사이트, 특정 앱 등)에 넣어서 사용하실 계획인가요? 활용WebRTC는 RTSP(`rtsp://...`)처럼 주소만 넣으면 플레이어(VLC 등)에서 바로 열리는 방식이 아닙니다. 브라우저와 서버가 서로 사양을 확인하는 **시그널링(Signaling)** 절차와 **WHEP(WebRTC-HTTP Egress Protocol)**이라는 표준 규약을 따르기 때문입니다.

하지만, **"주소처럼 쓸 수 있는"** 방법은 크게 두 가지가 있습니다.

---

### 1. WHEP URL (가장 표준적인 방법)
최근 WebRTC 스트리밍 서비스들은 **WHEP**라는 표준을 사용해 주소 하나로 스트림을 주고받습니다. MediaMTX도 이를 지원합니다.

*   **WHEP 주소 형식:** `http://192.168.0.200:8889/test`
*   **사용 방법:** 이 주소는 브라우저 주소창에 치는 용도가 아니라, **WHEP를 지원하는 플레이어(예: [Video.js WebRTC](https://videojs.github.io/videojs-webrtc-whep/) 또는 특정 모니터링 툴)**에 입력하는 용도입니다.

### 2. iframe을 이용한 웹 페이지 삽입
파이썬이나 자바스크립트로 직접 페이지를 만들고 있다면, MediaMTX가 제공하는 페이지를 `<iframe>`으로 불러오는 것이 가장 속 편한 방법입니다.
```html
<iframe src="[http://192.168.0.200:8889/test](http://192.168.0.200:8889/test)" width="640" height="480"></iframe>
```
이 방식은 MediaMTX가 복잡한 WebRTC 연결 로직을 다 처리해주기 때문에, 개발자는 주소만 갖다 쓰면 됩니다.
