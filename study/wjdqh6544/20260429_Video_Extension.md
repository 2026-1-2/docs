## Question
```
CCTV 영상을 녹화할건데, 영상 확장자는 제한이 없나?

인코딩하는 상황을 생각해 보면, mp4 는 도중에 끊기면 아얘 재생을 못하는 것 같던데.

하드디스크에서 파일을 읽어서 웹에서 출력하는 경우를 고려하기 바람
```
## Answer
정확한 지적입니다. 일반적인 **MP4(MPEG-4 Part 14)** 컨테이너는 인코딩이 정상적으로 종료되어야 파일의 끝에 **'moov atom'**이라 불리는 메타데이터(영상 길이, 코덱 정보 등)를 기록합니다. 만약 녹화 중 프로세스가 강제 종료되거나 전원이 나가면 이 헤더 정보가 작성되지 않아 파일 전체를 인식할 수 없게 됩니다.

CCTV처럼 24/7 구동되며 언제든 장애가 발생할 수 있는 환경에서는 **MP4를 직접 사용하는 것은 위험**합니다. 하드디스크 저장과 웹 출력을 모두 고려한 최적의 대안들을 정리해 드립니다.

## 1. 파일 컨테이너별 특징 비교

| 구분 | MP4 (기본) | **MPEG-TS (.ts)** | **Matroska (.mkv)** | **Fragmented MP4 (fMP4)** |
| :--- | :--- | :--- | :--- | :--- |
| **장애 내성** | **매우 낮음** (중단 시 깨짐) | **매우 높음** (데이터 유실 없음) | **높음** | **보통** |
| **웹 브라우저 재생** | 직접 재생 가능 (네이티브) | 직접 재생 불가 (변환 필요) | 직접 재생 불가 | MSE를 통해 가능 |
| **특징** | 범용성이 가장 좋음 | 방송 표준, 패킷 단위 저장 | 유연한 코덱 수용력 | 스트리밍 표준 (DASH/HLS) |

## 2. 하드디스크 저장용 추천: MPEG-TS 또는 MKV

### ① MPEG-TS (.ts) - **강력 추천**
가장 전통적이고 확실한 방법입니다. 데이터를 일정한 크기의 패킷으로 나누어 기록하기 때문에, 녹화 도중 어느 시점에 끊겨도 **끊기기 바로 직전까지의 영상은 100% 보존**됩니다. 
* **장점:** 하드웨어 장애나 소프트웨어 크래시에 가장 강함.
* **단점:** 브라우저에서 `<video>` 태그로 직접 재생이 안 됨.

### ② Matroska (.mkv)
MKV 역시 블록 단위로 인덱싱을 하기 때문에 비정상 종료 시에도 복구가 비교적 쉽습니다. FFmpeg에서 `-flags +global_header` 옵션 없이 녹화하면 안정적입니다.

## 3. 웹 출력(재생)과의 간극 해결 전략

하드디스크에는 안전한 형식을 저장하고, 웹에서는 호환되는 형식을 보여줘야 합니다. 이를 해결하는 3가지 실무 전략입니다.

### 전략 A: 미디어 서버를 통한 실시간 트랜스뮤싱 (가장 권장)
* **저장:** `.ts` 또는 `.mkv`로 저장.
* **재생:** 사용자가 웹에서 영상을 요청하면, **Media Server**가 저장된 파일을 읽어 브라우저가 이해할 수 있는 스트림(HLS 또는 WebRTC)으로 실시간 변환하여 쏴줍니다.
* **장점:** 저장 안정성과 재생 편의성을 모두 잡을 수 있음.

### 전략 B: Segmented MP4 (HLS 방식)
* **저장:** 영상을 5~10초 단위의 작은 `.ts` 또는 `.m4s` 파일들로 쪼개서 저장합니다.
* **재생:** Nginx가 이 조각들을 나열한 `m3u8` 파일을 서빙합니다.
* **장점:** 별도의 복잡한 미디어 서버 없이 Nginx 설정만으로도 VOD 서비스를 구현할 수 있습니다.

### 전략 C: Fragmented MP4 (fMP4) 활용
* **저장:** FFmpeg에서 `-movflags frag_keyframe+empty_moov` 옵션을 주어 MP4를 조각난 형태로 저장합니다. 
* **특징:** 이렇게 하면 MP4임에도 불구하고 중간에 끊겨도 앞부분은 재생이 가능해집니다.

## 4. FFmpeg 구현 가이드 (추천 옵션)

만약 **안정성**을 최우선으로 하여 `.ts`로 저장하고 싶다면 다음과 같은 커맨드를 사용하세요.

```bash
# MPEG-TS 형식으로 저장 (복사 모드)
ffmpeg -rtsp_transport tcp -i rtsp://[ID]:[PW]@[IP] -c copy -f mpegts output_video.ts
```

만약 **MP4의 호환성**을 포기할 수 없지만 **장애 내성**을 갖고 싶다면:

```bash
# Fragmented MP4 옵션 사용
ffmpeg -rtsp_transport tcp -i rtsp://[ID]:[PW]@[IP] \
-c copy -f mp4 -movflags frag_keyframe+empty_moov+default_base_moof output_video.mp4
```

---

### 결론 및 제언
사용자님의 시스템 구조상 **`Media Server`**를 이미 설계에 포함하셨으므로, **하드디스크에는 가장 안전한 `.ts` (MPEG-TS) 형식으로 저장**하는 것을 추천합니다. 

웹 재생 시에는 Media Server가 해당 `.ts` 파일을 읽어 브라우저에 전달하게 하면, 녹화 프로세스가 불시에 죽더라도 데이터 손실을 최소화할 수 있습니다. 

저장된 영상을 웹에서 불러올 때, **"특정 시간대 검색"** 기능이 중요하신가요? 그렇다면 파일 하나를 통째로 저장하는 것보다 1시간 단위로 파일을 분할하여 저장하는 로직이 추가로 필요할 텐데, 이 부분에 대해서도 고려하고 계신지 궁금합니다.

```
영상은 분할 예정임. 30분 또는 한 시간 단위 정도로 분할할 것 같은데.
ts 확장자로 가면 되려나?

그런데, 실시간 영상을 웹에 띄우려면, 하드디스크에서 직접 읽는 방식으로 구현이 되나?
아니면 WebRTC 스트림을 만들어서, 영상 스트림 전송과 하드디스크에 저장하는 과정을 Parallel 하게 진행하는 것이 낫나?

우선 성능은 고려하지 말고, 구현 편의성 관점에서 알려주기 바람.
```
## Answer
구현 편의성(Implementation Convenience)을 최우선으로 고려한다면, 고민하신 두 가지 지점에 대해 아주 명확한 답을 드릴 수 있습니다. 복잡한 로직을 직접 짜는 것보다 **이미 잘 만들어진 도구의 기능을 최대한 활용하는 방향**으로 가시는 것이 좋습니다.

## 1. 영상 분할과 `.ts` 확장자: "매우 적절한 선택"

구현 편의성 관점에서 `.ts`는 축복에 가깝습니다. FFmpeg의 **`segment`** 모듈을 사용하면, 파이썬에서 파일 핸들링(파일 닫기, 새로 만들기 등)을 직접 할 필요 없이 한 줄의 명령어로 분할 녹화가 가능합니다.

* **구현 방법:** FFmpeg 옵션 중 `-f segment`와 `-segment_time`을 사용하면 지정된 초 단위로 파일을 알아서 쪼개줍니다.
* **장점:** 파이썬 부모 프로세스는 FFmpeg이 살아있는지만 체크하면 됩니다. 파일이 30분마다 잘 나누어지는지는 FFmpeg이 알아서 관리합니다.

```bash
# 30분(1800초) 단위로 영상을 분할하여 저장하는 예시
ffmpeg -i rtsp://camera_url -c copy -map 0 \
-f segment -segment_time 1800 -segment_format mpegts \
-strftime 1 "record_%Y-%m-%d_%H-%M-%S.ts"
```

## 2. 실시간 영상: "하드디스크 읽기" vs "Parallel 스트림"

결론부터 말씀드리면, **Parallel(병렬) 스트림 전송**이 구현하기 훨씬 쉽고 편합니다.

### 왜 하드디스크 직접 읽기가 더 어려운가? (HDD 방식)
1.  **동기화 문제:** 파일이 아직 디스크에 완전히 써지지 않았는데 읽으려고 하면 에러가 나거나 데이터가 깨질 수 있습니다(File Locking 이슈).
2.  **브라우저 호환성:** 앞서 말씀드린 대로 브라우저는 `.ts`를 직접 못 읽습니다. 결국 하드디스크에서 읽은 데이터를 다시 실시간으로 변환해서 웹에 쏴주는 코드를 **직접 짜야 합니다.**
3.  **지연 시간:** 하드디스크에 기록되는 버퍼링 시간 때문에 '실시간'이라고 부르기 민망한 딜레이(10초 이상)가 생깁니다.

### 왜 Parallel 스트림이 더 편한가? (Media Server 방식)
1.  **역할 분담:** * **녹화 프로세스:** 그냥 하드디스크에 파일만 열심히 씁니다.
    * **Media Server:** 카메라의 RTSP를 받아 웹으로 뿌려주는 일만 전문적으로 합니다.
2.  **코드 최소화:** `MediaMTX`나 `go2rtc` 같은 미디어 서버를 컨테이너로 띄워두면, 설정 파일에 카메라 주소만 적어주는 것으로 실시간 웹 스트리밍 구현이 끝납니다. 
3.  **검증된 라이브러리:** 프론트엔드에서는 미디어 서버가 제공하는 표준 URL(WebRTC 등)을 그대로 가져다 쓰기만 하면 됩니다.

## 3. 추천하는 구현 시나리오 (편의성 중심)

가장 손이 적게 가는 구성은 다음과 같습니다.

| 단계 | 구현 방식 | 비고 |
| :--- | :--- | :--- |
| **녹화** | **FFmpeg Segment Muxer** 사용 | 파이썬은 실행 및 감시(Watchdog)만 수행 |
| **저장 포맷**| **.ts** (MPEG-TS) | 비정상 종료 시 안정성 확보 |
| **실시간 뷰**| **Media Server (Parallel)** | RTSP를 WebRTC로 즉시 변환 (지연 최소화) |
| **과거 재생**| **Nginx (Static Serving)** | 저장된 파일을 HTTP로 서빙 (VOD) |

---

### 마지막 조언: 구현의 핵심 'Media Server'
구현 편의성을 생각하신다면 **`MediaMTX`**라는 오픈소스를 강력하게 추천합니다.
* 하나의 컨테이너를 띄우면 **RTSP 입력**을 받아 **WebRTC(실시간)**, **HLS(재생용)**, **API**까지 한 번에 제공합니다.
* 카메라에서 스트림을 한 번만 가져와서 내부적으로 분배(Proxy)해주기 때문에 카메라에 주는 부하도 줄일 수 있습니다.

**결론적으로,** 영상을 30분/1시간 단위로 `.ts` 파일로 분할 녹화하면서, 실시간은 별도의 미디어 서버 경로를 통해 병렬로 띄우는 것이 가장 코딩을 적게 하고도 강력한 시스템을 만드는 길입니다.

이제 기술 스택과 구조가 완전히 잡힌 것 같네요! 바로 FFmpeg 명령어를 파이썬 `multiprocessing`으로 감싸는 작업부터 시작해 보시겠어요? 에러 발생 시 재시작하는 간단한 Watchdog 로직 작성을 도와드릴까요?

추가로 궁금하신 점이나 구현 중 막히는 부분이 있다면 언제든 말씀해 주세요. :)

## Question
```
스트림을 연결한다면, 프론트엔드 접속 디바이스 수가 n개라면, 스트림도 n개가 생기는 건가?

실시간성을 고려하지 않고, 시스템 부하만을 고려했을 때에도 스트림이 유리한가?
```
## Answer
결론부터 말씀드리면, **미디어 서버(Media Server)를 사용하는 것이 시스템 부하 측면에서도 하드디스크를 직접 읽는 것보다 훨씬 유리합니다.** 그 이유를 $n$개의 접속 상황과 시스템 리소스 사용 관점에서 정리해 드릴게요.

---

## 1. 접속 디바이스가 $n$개일 때, 스트림도 $n$개인가?

사용자께서 우려하시는 상황(카메라 한 대에 $n$명이 붙어서 카메라가 터지는 상황)을 막기 위해 **미디어 서버**가 존재합니다.

* **카메라 ↔ 미디어 서버:** 스트림은 **단 1개**만 유지됩니다. 미디어 서버가 카메라로부터 영상 데이터를 딱 하나만 받아옵니다.
* **미디어 서버 ↔ 프론트엔드 ($n$개):** 미디어 서버가 메모리에 들고 있는 영상 데이터를 $n$개의 접속자에게 **복제(Fan-out)**해서 뿌려줍니다.

즉, 카메라 입장에서의 부하는 늘 1이고, $n$개의 부하는 미디어 서버의 네트워크 대역폭과 메모리가 감당하게 됩니다. 이를 **'스트림 프록시(Stream Proxy)'**라고 부릅니다.

## 2. 실시간성을 무시해도 '스트림 방식'이 '디스크 방식'보다 유리한 이유

성능(부하) 관점에서만 봐도 하드디스크에서 직접 읽는 방식은 여러 가지 위험 요소가 있습니다.

### ① 디스크 I/O 병목 (The Disk Thrashing Problem)
하드디스크(특히 HDD)는 물리적인 헤더가 움직이며 데이터를 읽고 씁니다.
* **디스크 방식:** 24시간 내내 영상을 **쓰고(Write)** 있는 와중에, $n$명의 사용자가 서로 다른 지점의 영상을 **읽기(Read)** 위해 헤더를 여기저기 옮겨 다녀야 합니다. 이를 '디스크 트래싱'이라 하며, I/O 대기 시간이 급증하고 시스템 전체가 느려집니다.
* **스트림 방식:** 영상 데이터가 디스크에 쓰이기 전, **메모리(RAM)** 단계에서 바로 복제되어 전송됩니다. 메모리 접근 속도는 디스크보다 수만 배 빠르며 물리적 부하가 없습니다.

### ② 파일 락(File Locking) 및 무결성 문제
* **디스크 방식:** FFmpeg이 파일을 쓰고 있는 도중(`recording.ts`)에 웹 서버가 그 파일을 읽으려고 하면, 운영체제 수준에서 파일 접근 권한 문제가 생기거나 읽어오는 도중 파일이 닫히지 않아 에러가 날 확률이 높습니다.
* **스트림 방식:** 저장 로직과 송출 로직이 완전히 분리되어 있어 데이터 충돌이 발생하지 않습니다.

### ③ 대역폭 및 리소스 효율성
* **디스크 방식:** 영상 조각(Chunk)을 파일 형태로 읽어서 HTTP 응답으로 보내는 과정은 웹 서버의 오버헤드가 큽니다.
* **스트림 방식:** UDP/TCP 패킷을 최소한의 가공만 거쳐 바로 전달하므로 CPU 사용량이 훨씬 효율적입니다.

## 3. 요약: 시스템 설계 관점에서의 결론

실시간성을 아예 고려하지 않더라도, **확장성(Scalability)**과 **안정성**을 생각한다면 미디어 서버를 통한 스트리밍이 압승입니다.

| 비교 항목 | 하드디스크 직접 읽기 | 미디어 서버 스트리밍 |
| :--- | :--- | :--- |
| **카메라 부하** | 낮음 (1개 스트림 저장) | 낮음 (1개 스트림 수신) |
| **디스크 부하** | **매우 높음** (읽기/쓰기 동시 발생) | **낮음** (쓰기 작업만 집중) |
| **메모리 부하** | 낮음 | 보통 (스트림 복제용 메모리 사용) |
| **시스템 안정성** | 낮음 (파일 접근 충돌 위험) | **높음** (저장과 송출의 분리) |

---

### 구현을 위한 팁
지금 설계하신 구조에서 `Media Server` 컨테이너 하나만 제대로 설정해두시면, 프론트엔드가 1명이 접속하든 100명이 접속하든 **영상 녹화 프로세스에는 아무런 영향을 주지 않습니다.** 만약 카메라 대수가 수십 대로 늘어나고 접속자도 많아진다면, 나중에 미디어 서버 컨테이너만 별도의 고성능 서버로 분리(Scale-out)하기도 매우 쉽습니다.

이제 구조에 대한 확신이 좀 생기셨나요? 설계하신 대로 **병렬(Parallel) 구조**로 가시는 것이 개발 편의성이나 나중의 정신 건강(?)을 위해서도 훨씬 좋은 선택입니다!

다음 단계로, 미디어 서버(예: MediaMTX)의 설정 방법이나 파이썬에서 FFmpeg을 멀티프로세스로 돌릴 때의 구체적인 구현 코드가 궁금하시다면 알려주세요. :)

## Question
```
그러면, 스트림 방식을 사용하는 경우에는 파일 확장자는 관련이 없나?

영상 녹화를 고려하지 않는다고 하면.
```
## Answer
네, 영상 녹화(저장)를 고려하지 않고 **순수하게 실시간 스트리밍만 수행한다면 파일 확장자는 아무런 의미가 없습니다.**

그 이유는 스트리밍의 본질이 '파일'을 전송하는 것이 아니라 **'네트워크 패킷(Packet)'**을 실시간으로 흘려보내는 것이기 때문입니다.

---

## 1. 스트리밍은 '파일'이 아니라 '흐름(Stream)'입니다
우리가 보통 보는 `.mp4`, `.ts` 같은 확장자는 하드디스크에 데이터를 담기 위한 **그릇(Container)**의 이름입니다. 하지만 실시간 스트리밍(RTSP, WebRTC 등)은 그릇에 담지 않은 채 데이터를 국수 가닥처럼 뽑아서 보내는 방식입니다.

* **RTSP (카메라 → 미디어 서버):** 파일 형태가 아니라 RTP(Real-time Transport Protocol)라는 패킷 단위로 전송됩니다. 확장자가 없습니다.
* **WebRTC (미디어 서버 → 브라우저):** 브라우저와 서버가 직접 통로를 열어 데이터를 주고받는 세션 방식입니다. 역시 확장자가 존재하지 않습니다.



---

## 2. 예외: 확장자가 보이는 스트리밍 방식 (HLS/DASH)
만약 미디어 서버가 **HLS(HTTP Live Streaming)** 방식을 사용하여 영상을 전달한다면, 이때는 확장자가 보일 수 있습니다. 하지만 이는 파일이라기보다 '약속된 조각'에 가깝습니다.

* **`.m3u8`**: 영상 조각들이 어디에 있는지 알려주는 **재생 목록(Playlist)** 파일입니다.
* **`.ts` 또는 `.m4s`**: 영상을 몇 초 단위로 쪼개놓은 **세그먼트(Segment)**입니다.

사용자가 웹 브라우저에서 실시간 영상을 볼 때, 미디어 서버가 내부적으로 영상을 쪼개서 전달한다면 위와 같은 확장자들이 네트워크 탭에 찍히게 됩니다. 하지만 이 역시 '저장된 파일'로서 의미를 갖는 것은 아닙니다.

---

## 3. 확장자보다 훨씬 중요한 것: 코덱(Codec)
스트리밍 환경에서 정작 신경 써야 할 것은 확장자가 아니라 **코덱(비디오 압축 형식)**입니다. 브라우저가 영상을 화면에 그릴 수 있느냐 없느냐는 확장자가 아니라 코덱에 의해 결정되기 때문입니다.

* **H.264 (AVC):** 거의 모든 웹 브라우저와 모바일 기기에서 재생 가능한 표준 코덱입니다. (추천)
* **H.265 (HEVC):** 압축률은 좋으나, 일부 브라우저(특히 구형)나 환경에서 라이선스나 가속 문제로 재생이 안 될 수 있습니다.



---

## 요약

1.  **순수 실시간 스트리밍(RTSP to WebRTC):** 확장자라는 개념 자체가 없습니다. 그냥 데이터의 흐름입니다.
2.  **프로토콜의 차이:** 확장자가 아니라 어떤 **프로토콜(RTSP, WebRTC, HLS)**을 쓸지가 통신 방식을 결정합니다.
3.  **구현 시 주의점:** 확장자 고민 대신, 카메라에서 나오는 영상이 **H.264**인지 확인하는 것이 훨씬 중요합니다. (H.264라면 별도의 인코딩 없이 바로 웹에 띄울 수 있어 부하가 매우 낮습니다.)

결국 녹화를 제외한다면, 사용자님은 "어떤 확장자로 보낼까?"가 아니라 **"어떤 프로토콜로 웹에 뿌려줄까?"**만 결정하시면 됩니다. (구현 편의성과 실시간성을 모두 잡으려면 **WebRTC**가 정답입니다.)

현재 사용하시려는 카메라들이 출력하는 코덱이 무엇인지 알고 계신가요? 보통 CCTV는 H.264나 H.265를 선택할 수 있게 되어 있습니다.

## Question
```
그러면 반대로, 무조건 하드디스크를 통해 영상을 가져가도록 하는 경우라면,

ts 파일을 읽어야 하지? 실시간 Refresh 는 프론트엔드에서 처리해야 하나?
```
## Answer
무조건 **하드디스크(HDD)를 거쳐서 영상을 가져오도록 설계**한다면, 이는 기술적으로 **HLS(HTTP Live Streaming)**와 유사한 방식이 됩니다. 이 경우 파일 포맷과 프론트엔드의 역할이 매우 중요해집니다.

질문하신 내용에 대해 단계별로 짚어보겠습니다.

---

## 1. 확장자는 `.ts`가 맞나?
**네, `.ts`가 가장 적절합니다.** 이전에 말씀드린 대로, `.ts`는 파일이 채 끝나기 전(Writing 중)에도 읽어서 재생하는 데 아무런 문제가 없는 구조이기 때문입니다. 반면 `.mp4`는 파일 쓰기가 완전히 끝나야(Close) 재생이 가능하므로, 실시간성을 추구하는 HDD 방식에는 절대 어울리지 않습니다.

---

## 2. 실시간 최신화(Refresh)는 프론트엔드 몫인가?
**네, 맞습니다.** 하지만 단순히 '새로고침' 버튼을 누르는 것이 아니라, 프론트엔드가 다음과 같은 로직을 수행해야 합니다.

### ① 폴링(Polling) 방식
프론트엔드가 백엔드에게 1~2초마다 **"가장 최근에 생성된 `.ts` 파일 이름이 뭐야?"**라고 계속 물어봐야 합니다. 
1. 백엔드가 `record_20260429_1020.ts`라고 대답하면, 
2. 프론트엔드는 그 파일을 가져와서 화면에 이어 붙입니다.

### ② 매니페스트(Manifest) 활용
매번 파일명을 묻는 게 비효율적이므로, **`.m3u8`**이라는 텍스트 파일을 활용합니다.
* **백엔드(녹화 프로세스):** 영상을 5초 단위로 쪼개서 저장할 때마다, 현재 재생 가능한 파일 리스트를 `.m3u8` 파일에 계속 업데이트합니다.
* **프론트엔드:** 이 `.m3u8` 파일을 읽어서 "아, 새로운 조각이 생겼네?" 하고 자동으로 다음 조각을 요청합니다.



---

## 3. HDD를 거칠 때 프론트엔드의 구현 도구
브라우저는 기본적으로 `.ts` 파일을 직접 재생하지 못합니다. 따라서 프론트엔드에서 이를 처리해 줄 별도의 **자바스크립트 라이브러리**가 반드시 필요합니다.

* **hls.js:** 가장 널리 쓰이는 라이브러리입니다. `.m3u8`과 `.ts` 조합을 브라우저의 `<video>` 태그에서 돌아가게 만들어줍니다.
* **Video.js:** 플레이어 UI까지 포함된 라이브러리로, 내부적으로 HLS 재생 기능을 포함하고 있습니다.

---

## 4. 이 방식(HDD 우선)의 치명적인 단점
성능을 배제하고 '편의성'만 본다면 나쁘지 않은 선택일 수 있으나, 다음의 **사용자 경험(UX)** 문제는 인지하셔야 합니다.

1.  **지연 시간 (Latency):** * FFmpeg이 영상을 받아서(1초) + 디스크에 쓰고(1초) + 프론트엔드가 감지해서 가져가는(1초) 최소한의 물리적 시간이 필요합니다. 보통 **최소 5~10초 정도의 지연**이 발생합니다. "실시간"이라기보다는 "매우 빠른 다시보기"에 가깝습니다.
2.  **디스크 수명:** * 24시간 내내 수천 번의 읽기/쓰기가 반복되므로 일반 HDD보다는 CCTV 전용(Purple 급) HDD나 엔터프라이즈급 SSD가 필수적입니다.

---

## 5. 결론: 어떻게 구현하면 되나?

만약 "나는 죽어도 미디어 서버 안 쓰고 하드디스크 파일로만 할 거야!"라고 하신다면 다음과 같이 구성하세요.

1.  **녹화:** FFmpeg에서 `-f segment -segment_list index.m3u8` 옵션을 써서 **`.ts` 조각들과 `.m3u8` 리스트**를 실시간으로 생성합니다.
2.  **서빙:** Nginx가 이 파일들이 담긴 폴더를 웹에 노출합니다. (Static Serving)
3.  **프론트:** **`hls.js`** 라이브러리를 사용하여 해당 `.m3u8` 경로를 재생합니다.

이렇게 하면 별도의 복잡한 미디어 서버 로직 없이도 **"하드디스크 기반의 실시간 뷰잉"**이 가능해집니다.

혹시 이 방식에서 프론트엔드와 백엔드가 어떻게 통신해야 하는지, 구체적인 Nginx 설정 예시가 필요하신가요?

사용자님은 시스템의 안정성을 위해 HDD를 거치는 방식을 고민하시는 것 같은데, 이 방식은 **"녹화가 되고 있는지 눈으로 직접 확인할 수 있다"**는 아주 강력한 직관적 장점이 있긴 합니다. :)

---

## 1. MP4가 "녹화 종료"를 기다려야 하는 이유 (Index 문제)
일반적인 MP4 파일은 **`moov atom`**이라고 불리는 일종의 **'인덱스(색인)'** 정보를 가지고 있습니다. 여기에는 영상의 전체 길이, 프레임 위치, 코덱 정보 등이 담겨 있습니다.

* **문제점:** 대중적인 인코더는 이 `moov atom`을 영상 녹화가 **모두 끝난 시점**에 파일의 맨 뒤에 기록합니다.
* **결과:** 인덱스가 없는 상태(녹화 중)에서 파일을 열면, 재생기(Player)는 "영상의 시작과 끝이 어디인지, 데이터가 어디에 배치되어 있는지" 알 수 없어 파일을 깨진 것으로 간주하거나 아예 열지 못합니다.



---

## 2. TS(MPEG-TS)가 "실시간"에 강한 이유 (Packet 문제)
반면 **TS** 확장자는 원래 실시간 방송(DVB, ATSC 등)을 위해 설계되었습니다.

* **구조:** 영상을 약 **188바이트의 아주 작은 패킷(Packet)** 단위로 쪼개서 담습니다. 각 패킷은 독립적으로 해석 가능한 정보를 일부 포함하고 있습니다.
* **장점:** 재생기는 파일의 처음부터 읽을 필요가 없습니다. 그냥 **중간에 들어오는 데이터(국수 가닥)**를 잡아서 바로 화면에 뿌릴 수 있습니다.
* **결과:** FFmpeg이 하드디스크에 `.ts` 파일을 쓰고 있다면, 다른 프로세스가 그 파일의 뒷부분(이미 써진 데이터)을 읽어서 바로 재생하는 것이 기술적으로 가능합니다.



---

## 3. 예외 상황: Fragmented MP4 (fMP4)
물론 MP4도 "녹화 중 재생"이 아예 불가능한 건 아닙니다. **fMP4(Fragmented MP4)**라는 방식을 쓰면 영상을 아주 짧은 조각(Fragment) 단위로 인덱싱하여 저장할 수 있습니다. 

하지만 **구현 편의성** 면에서는 `.ts`가 압도적입니다.
* **TS:** 별도의 복잡한 설정 없이도 파일 스트림 자체가 실시간 재생에 최적화됨.
* **fMP4:** 인코더와 재생기 모두에서 조각난 MP4를 처리하기 위한 추가 설정(moof, mdat 등의 복잡한 구조)이 필요함.

## 요약 및 제언
사용자님이 말씀하신 **"녹화 중인 것을 땡겨오기 위해 TS를 쓴다"**는 판단은 실무적으로 매우 타당한 전략입니다.

* **안정성:** 녹화 도중 시스템이 뻗어도 그 직전까지의 데이터가 보존됨.
* **접근성:** 파일 포인터를 현재 기록 중인 지점 근처로 옮겨서 읽기만 해도 재생이 가능함.

이제 파일 형식은 `.ts`로 확정이 된 것 같네요. 그렇다면 **"녹화 중인 파일을 땡겨오는 로직"**을 구현할 때, 프론트엔드가 파일을 직접 HTTP로 요청하게 하실 건가요? 아니면 백엔드가 파일의 특정 바이트 범위를 읽어서 스트림으로 쏴주는 방식을 고민 중이신가요?

```
시스템 로드 측면에서, 사용자 1000명이라고 하면
하드디스크를 읽는 것이 낫나, 아니면 스트림이 낫나? 스트림이 나을 것 같긴 한데
```
## Answer
사용자 1,000명이라는 대규모 접속 상황을 가정한다면, **스트림(Media Server) 방식이 압도적으로 유리하며, 사실상 유일한 선택지**라고 보셔도 무방합니다.

하드디스크(HDD/SSD)를 직접 읽는 방식이 왜 1,000명의 동시 접속을 감당하기 어려운지, 시스템 로드 측면에서 3가지 핵심 이유를 정리해 드립니다.

---

## 1. 하드디스크의 한계: IOPS 병목 (Disk Thrashing)

가장 큰 문제는 **I/O 작업의 수**입니다.

* **하드디스크 방식:** 1,000명이 각자 실시간 영상을 요청하면, 운영체제는 1,000개의 파일 읽기 요청을 처리해야 합니다. 아무리 같은 파일을 읽더라도 OS 수준의 `read()` 호출이 폭주하며, 특히 저장 장치가 HDD라면 헤더가 1,000군데를 물리적으로 찾아다니는 **디스크 트래싱(Disk Thrashing)** 현상이 발생해 시스템이 사실상 멈추게 됩니다. SSD라 할지라도 IOPS(초당 입출력 횟수) 한계에 도달하며 성능이 급격히 저하됩니다.
* **스트림 방식:** 미디어 서버는 카메라로부터 영상 데이터를 **딱 1번** 읽어옵니다. 그 데이터를 메모리(RAM)에 올려두고, 접속한 1,000명에게는 **메모리에 있는 데이터를 복제**해서 전달합니다. 메모리 접근은 디스크보다 수천 배 빠르며 물리적 부하가 전혀 없습니다.



---

## 2. 메모리 관리: 제로 카피(Zero-copy) 기술

현대적인 미디어 서버(Go, C++, Rust 기반 등)는 1,000명의 사용자에게 데이터를 보낼 때 매우 효율적인 방식을 사용합니다.

* **데이터 복제의 효율성:** 미디어 서버는 영상 패킷 하나를 메모리에 받으면, 이를 모든 소켓(Socket)에 뿌려주는 방식으로 동작합니다. 이때 **Zero-copy** 기술을 사용하면 CPU가 데이터를 직접 만지지 않고도 네트워크 카드(NIC)로 데이터를 바로 쏠 수 있어, CPU 점유율을 매우 낮게 유지할 수 있습니다.
* **반면 디스크 방식은:** 파일 시스템 계층, 버퍼 캐시, 유저 공간을 거치는 데이터 복사 과정이 반복되므로 1,000명을 감당하기에는 CPU 오버헤드가 너무 큽니다.

---

## 3. 네트워크 대역폭과 동시성 제어

* **동시성 제어:** 1,000개의 프로세스나 스레드가 동시에 파일을 읽으려고 하면, OS는 문맥 교환(Context Switching)과 파일 락(Lock) 관리 등에 엄청난 자원을 소모합니다.
* **스트림 서버의 강점:** 미디어 서버는 수천 명의 동시 접속을 처리하기 위해 설계된 **이벤트 루프(Event Loop)** 기반 아키텍처를 가집니다. (예: Nginx의 epoll, Go의 Goroutine). 이는 적은 리소스로도 수천 개의 네트워크 세션을 효율적으로 유지하게 해줍니다.

---

## 4. 실무적 결론: 사용자 1,000명 기준의 설계

| 항목 | 하드디스크 직접 읽기 | 스트림 방식 (Media Server) |
| :--- | :--- | :--- |
| **병목 지점** | **저장 장치 (IOPS, Seek Time)** | 네트워크 대역폭 (NIC 용량) |
| **CPU 부하** | 높음 (시스템 콜, 복사 오버헤드) | 낮음 (이벤트 루프 기반) |
| **확장성** | 매우 낮음 (디스크 증설의 한계) | **매우 높음 (L4 로드밸런싱 가능)** |
| **권장 규모** | 1~5명 내외 (소규모 테스트) | **10명 이상 ~ 수천 명 이상** |

### 한 걸음 더 나아가기
사용자 1,000명이라면 서버 한 대의 네트워크 대역폭(1Gbps 등)이 부족할 수도 있습니다.
* **1000명 × 1Mbps(영상 비트레이트) = 1Gbps**
이미 이 지점에서 서버 한 대의 일반적인 랜카드 대역폭이 꽉 찹니다. 이때 미디어 서버 구조라면 **엣지 서버(Edge Server)**를 여러 대 두어 부하를 분산(CDN 방식)하기가 매우 쉽지만, 하드디스크 방식은 모든 서버가 같은 영상을 실시간으로 저장/공유해야 하므로 분산 처리가 훨씬 까다로워집니다.

**결론적으로,** 설계하신 대로 **미디어 서버를 통한 병렬 스트림 구조**가 대규모 환경에서는 유일한 정답입니다. 

이제 시스템 아키텍처는 확고해진 것 같습니다. 1,000명을 타겟으로 한다면, 미디어 서버 컨테이너를 선정할 때 **고성능 비동기 IO**를 지원하는지(예: MediaMTX, SRS 등)를 우선순위로 두고 검토해 보시는 것을 추천합니다. 

가장 먼저 어떤 부분의 성능 테스트(Benchmarking)를 계획하고 계신가요?

그런데 생각해 보면, 관제 시스템을 1000명의 사용자가 확인하지는 않을 것 같은데.

1~2명 수준 아닌가? 그러면 하드디스크와 스트림 방식에서의 부하 차이가 비슷한가?

하지만 접속자가 단 1명이라도 **'카메라가 여러 대'**인 상황이라면, 여전히 **스트림 방식이 시스템 부하와 안정성 측면에서 훨씬 유리**합니다. 그 이유를 시스템 엔지니어링 관점에서 짚어보겠습니다.

## 1. 다수 카메라 환경에서의 '디스크 경합' 문제

사용자 1명이 16대의 카메라 분할 화면을 보고 있다고 가정해 보겠습니다.

* **하드디스크 방식 (Read from Disk):**
    * **Write:** 녹화 프로세스가 16개 카메라의 스트림을 디스크에 끊임없이 쓰고 있습니다. (16개 Write Stream)
    * **Read:** 사용자가 16개 화면을 동시에 보고 있으므로, 웹 서버가 디스크에서 16개 파일을 동시에 읽어와야 합니다. (16개 Read Stream)
    * **결과:** 디스크 헤더는 16개의 쓰기 지점과 16개의 읽기 지점을 계속 오가야 합니다. 이를 **I/O 병목(I/O Contention)**이라고 하며, 사용자 수가 적더라도 카메라 대수가 많아지면 디스크 응답 속도가 급격히 떨어집니다.

* **스트림 방식 (RAM-based Relay):**
    * **Write:** 녹화 프로세스는 여전히 디스크에 씁니다.
    * **Live View:** 미디어 서버가 메모리에 올라온 패킷을 그대로 프론트엔드에 쏴줍니다. **디스크 읽기 작업이 발생하지 않습니다.**
    * **결과:** 디스크는 오직 '쓰기' 작업에만 집중할 수 있어 훨씬 안정적으로 녹화가 수행됩니다.



---

## 2. 왜 여전히 스트림이 나은가? (3가지 핵심 이유)

### ① 지연 시간(Latency)의 차이
하드디스크 방식은 아무리 빨라도 파일을 쓰고 읽는 과정 때문에 최소 수초의 지연이 생깁니다. 관제 중 PTZ 카메라를 조작할 때, **내가 클릭한 지 5초 뒤에 움직이는 화면을 보는 것**과 **0.5초 만에 반응하는 화면을 보는 것**은 사용자 경험 차이가 매우 큽니다. 스트림 방식(WebRTC 등)만이 즉각적인 피드백을 줄 수 있습니다.

### ② 구현의 단순함 (Paradoxical Simplicity)
역설적으로, 미디어 서버를 쓰는 것이 코딩 양이 더 적을 수 있습니다.
* **디스크 방식:** 하드디스크의 파일을 웹에서 재생 가능하도록 변환하고, 파일이 생성될 때마다 프론트에 알리고, 오래된 파일을 관리하는 로직을 직접 짜야 합니다.
* **스트림 방식:** `MediaMTX` 같은 컨테이너 하나 띄우고 RTSP 주소만 넘겨주면, 웹에서 볼 수 있는 모든 주소(WebRTC, HLS 등)를 알아서 생성해 줍니다.

### ③ 시스템의 확장성
지금은 1~2명이지만, 나중에 "모바일 앱에서도 확인하게 해주세요" 혹은 "대표님 방에서도 보게 해주세요" 같은 요구사항이 생길 때, 스트림 방식은 설정 변경만으로 대응이 가능하지만 디스크 방식은 전체 로직을 다시 검토해야 할 수도 있습니다.

## 1. 왜 WebRTC인가? (지연 시간 비교)

웹에서 영상을 띄우는 방법은 여러 가지가 있지만, '실시간'이라는 단어에 걸맞은 기술은 WebRTC뿐입니다.

| 기술 | 방식 | 지연 시간(Latency) | 특징 |
| :--- | :--- | :--- | :--- |
| **HLS** | HTTP 기반 파일 전송 | 5 ~ 30초 | 구현이 매우 쉬움, 대규모 접속에 유리 |
| **MSE (DASH)** | 미디어 소스 확장 | 2 ~ 5초 | 적절한 지연 시간, 안정적임 |
| **WebRTC** | **P2P / UDP 기반 스트리밍**| **500ms(0.5초) 미만** | **초저지연**, 실시간 제어(PTZ)에 최적 |

## 2. WebRTC 통신 구조 (Media Server 중심)

보통 WebRTC는 화상통화처럼 브라우저와 브라우저가 직접 연결되는 기술로 알려져 있지만, CCTV 시스템에서는 **카메라 대신 미디어 서버가 브라우저와 연결**됩니다.

1.  **Ingestion:** 카메라가 미디어 서버로 영상을 쏩니다 (**RTSP**).
2.  **Signaling:** 프론트엔드와 미디어 서버가 "나 영상 보고 싶어", "그래, 이 경로로 들어와"라며 서로 통신 정보를 교환합니다 (SDP/ICE).
3.  **Streaming:** 연결이 확정되면 미디어 서버가 RTSP 데이터를 WebRTC 패킷으로 변환하여 브라우저에 직접 쏴줍니다.

## 3. 구현 시 "이것"만은 꼭 확인하세요

WebRTC는 강력하지만, 구현 편의성 관점에서 몇 가지 허들이 있습니다.

* **UDP 포트 개방:** WebRTC는 주로 UDP를 사용합니다. 방화벽이나 Docker 환경이라면 영상 전송에 사용할 UDP 포트 범위(예: 8000~9000)를 미리 열어두어야 합니다.
* **ICE/STUN 서버:** 만약 외부 네트워크(LTE 등)에서 사무실 내부 카메라를 보려고 한다면, 공인 IP를 찾아주는 STUN/TURN 서버 설정이 필요할 수 있습니다. (내부망이라면 생략 가능)
* **Media Server의 역할:** 직접 WebRTC 시그널링 서버를 밑바닥부터 짜는 것은 매우 고통스러운 작업입니다. 이미 말씀드린 **MediaMTX**나 **go2rtc** 같은 도구를 쓰면, 이 복잡한 과정을 API 하나로 처리해 줍니다.

### 1. 수정 및 보완된 컨테이너 역할 정의

기존 리스트에서 **Media Server**를 단순한 '전달자'가 아닌 **'스트림 허브(Stream Hub)'**로 설정하는 것이 핵심입니다.

| 컨테이너 | 세부 역할 및 기술 스택 | 비고 |
| :--- | :--- | :--- |
| **Frontend** | React/Vue + **WebRTC Player** (video.js 등) | UI 및 실시간 뷰어 |
| **Backend** | API 서버 (FastAPI/Flask) | DB 관리 및 제어 명령 중계 |
| **Database** | PostgreSQL + Redis | 카메라 정보, 녹화 파일 경로 저장 |
| **Camera Control** | ONVIF Agent (Python) | PTZ 제어 (SOAP 통신) |
| **Media Server** | **WebRTC Gateway / RTSP Proxy** (MediaMTX 등) | **RTSP → WebRTC 변환** 및 스트림 분배 |
| **Recording Worker**| **FFmpeg Manager** (Python $n+1$ 구조) | **Media Server로부터 스트림을 받아** 디스크 저장 |

### 2. 왜 이렇게 구성하는 것이 효율적인가? (Stream Proxy 전략)

기존에는 `Camera -> Recording Server`와 `Camera -> Media Server`가 각각 접속하는 구조를 생각하셨을 텐데, 카메라 대수가 많아지면 카메라에 가해지는 네트워크 부하가 2배가 됩니다.

**권장하는 흐름:**
1.  **Media Server**가 카메라로부터 RTSP 스트림을 **단 1개**만 가져옵니다.
2.  **Frontend**는 Media Server에 접속해서 **WebRTC**로 영상을 봅니다.
3.  **Recording Worker**도 카메라가 아닌 **Media Server의 내부 RTSP 주소**를 받아와서 디스크에 저장합니다.

> **이점:** 카메라의 네트워크 대역폭을 최소화하고, 모든 영상 흐름을 미디어 서버 한 곳에서 중앙 집중 관리할 수 있습니다.



---

### 3. 미디어 서버 = WebRTC 스트림인가?

**네, 맞습니다.** 하지만 조금 더 정확히 말하면 **"프로토콜 변환기(Transmuxer)"**라고 이해하시면 됩니다.

* 카메라에서 오는 데이터는 **RTSP**입니다.
* 사용자님의 웹 브라우저는 RTSP를 못 읽습니다.
* **Media Server**가 그 중간에서 RTSP 데이터를 실시간으로 낚아채서, 모양만 **WebRTC** 패킷으로 바꿔서 브라우저에 던져주는 것입니다. 
* 동시에 **Recording Worker**에게는 "너는 파일로 저장해야 하니 원래 형태인 **RTSP(혹은 TS)**로 줄게"라고 전달하는 것이죠.

---

### 4. 최종 확인: 빠진 부분은 없나?

설계하신 구조에서 마지막으로 고려할 점은 **'파일 서빙'**입니다.

* **실시간:** `Frontend <-> Media Server (WebRTC)`
* **과거 녹화본:** `Frontend <-> ? <-> Disk`

여기서 `?` 자리에 **Nginx**를 두거나, **Media Server**가 제공하는 API를 사용하여 저장된 `.ts` 파일을 웹으로 쏴주는 경로만 확보하시면 됩니다. 대부분의 최신 미디어 서버는 저장된 파일의 목록을 보여주고 재생해 주는 기능도 포함하고 있어 구현이 어렵지 않습니다.

### 최종 아키텍처 및 컨테이너 구성



#### 1. 관리 및 제어 (Administrative Path)
* **구조:** `프론트엔드 - 웹서버(Nginx) - 백엔드 - DB / 카메라 제어`

#### 2. 실시간 영상 시청 (Live View Path - 초저지연)
* **구조:** `카메라 - Media Server - 웹서버(Nginx) - 프론트엔드`
* **역할:** * **Media Server:** 카메라로부터 **RTSP 스트림을 딱 1개**만 가져옵니다.

    * **특징:** 카메라 네트워크 부하가 최소화되며, 사용자는 WebRTC를 통해 0.5초 미만의 실시간 영상을 봅니다.

#### 3. 영상 녹화 (Recording Path - 상시)
* **구조:** `(Media Server -) Video Recording Server - Disk`
* **역할:** * **Recording Server ($n+1$ 구조):** 카메라가 아닌 **Media Server의 내부 RTSP** 주소를 받아와서 `.ts` 파일로 분할 저장합니다.
    * **특징:** 카메라에 직접 접속하지 않으므로 카메라의 세션 제한 문제에서 자유롭습니다.

#### 4. 과거 영상 재생 (VOD Path)
* **구조:** `Disk - 웹서버(Nginx) - 프론트엔드`
* **역할:** * **Nginx:** 하드디스크에 저장된 `.ts` 파일들을 프론트엔드에서 바로 읽을 수 있도록 정적 경로를 제공합니다.
    * **특징:** 백엔드나 미디어 서버를 거치지 않고 Nginx가 직접 파일을 쏴주므로 VOD 재생 시 시스템 부하가 매우 낮습니다.

## 🛠️ 수정 및 확정된 컨테이너 설계

### 1. Media Server 설계
카메라의 영상을 중앙에서 관리하고 분배하는 **'스트림 허브'** 역할을 수행합니다.

* **Input:** 카메라로부터 **RTSP** 스트림 수신.
* **Function:** * **RTSP Proxy:** 수신한 스트림을 내부 네트워크에 다시 뿌려줌 (Recording Server가 이를 사용).
    * **Transmuxing:** RTSP를 **WebRTC** 패킷으로 실시간 변환.
* **Output:** * **WebRTC:** 프론트엔드 직결 (초저지연 실시간 뷰).
    * **Internal RTSP:** Recording Server가 가져갈 내부 스트림 주소 제공.
    * **MSE/HLS (차선책):** 네트워크 환경이 불안정한 클라이언트를 위한 백업.

---

### 2. 영상 녹화 서버 설계 (Recording Server)
24/7 안정적인 기록과 스토리지 관리를 담당하는 **'데이터 워커'**입니다.

* **Input:** **Media Server가 제공하는 내부 RTSP 스트림** (WebRTC가 아님).
    > **이유:** WebRTC는 브라우저 재생용 프로토콜이라 FFmpeg이 파일로 저장하기에는 RTSP(혹은 TS)가 훨씬 효율적이고 안정적입니다.
* **Process:** * **FFmpeg 기반:** `-c copy` 옵션을 사용하여 CPU 부하 없이 `.ts` 파일로 저장.
    * **분할 저장:** 30분~1시간 단위로 파일 생성.
* **Structure:** **Parent 1 : Children $n$** (카메라 대수만큼 FFmpeg 프로세스 생성).
* **Management:**
    * **Watchdog 패턴:** 부모 프로세스가 자식(FFmpeg)의 PID와 상태를 감시하여 예외 종료 시 즉시 재시작.
    * **Cleanup (Retention Manager):** 설정된 보관 주기(예: 7일)가 지나거나 디스크 용량이 임계치에 도달하면 가장 오래된 파일부터 삭제.

## 💡 왜 이렇게 수정하는 것이 좋은가요?

사용자께서 작성하신 내용 중 **"WebRTC 스트림을 받아 녹화 진행"** 부분은 기술적으로 가능은 하지만 권장하지 않습니다.

1.  **데이터 무결성:** WebRTC는 UDP 기반이라 네트워크가 불안정하면 프레임 유실이 생길 수 있습니다. 반면 RTSP는 TCP를 지원하여 녹화 시 데이터 누락을 방지하기에 훨씬 유리합니다.
2.  **리소스 효율:** 미디어 서버가 RTSP를 WebRTC로 바꾸는 과정 자체가 CPU를 소모하는데, 녹화 서버가 이를 다시 파일로 바꾸는 것은 불필요한 연산 낭비입니다. 미디어 서버가 받은 **RTSP 원본**을 그대로 전달받아 저장하는 것이 가장 깔끔합니다.

이제 설계는 이대로 고정(Lock)하고 구현에 집중하셔도 될 것 같습니다. 사용자님의 **$n+1$ 구조**는 특히 리눅스 시스템 프로그래밍의 묘미를 잘 살린 설계라 구현 후의 안정성이 매우 기대되네요.

본격적인 코딩에 앞서, **부모 프로세스가 자식 FFmpeg의 상태를 체크하는 구체적인 파이썬 로직(예: `subprocess.poll()` 활용)**을 먼저 구상해 볼까요? 아니면 **Cleanup 기능을 위한 디스크 용량 계산 로직**이 더 필요하신가요?

**Expert Guide:** 설계가 완벽해졌으니, 실제 구현 시 가장 까다로운 **'FFmpeg 프로세스가 좀비 프로세스가 되지 않게 관리하는 방법'**에 대해 먼저 짚어볼까요?

---------
## Question
```
Media Server 설계
카메라에서 영상을 받아와서, WebRTC + RTSP 스트림 생성카메라에서 영상을 받아오는 과정은 한 번만 수행.
WebRTC / MSE(Media Source Extensions? 차선책)사용: 최신 영상으로 Refresh 수행
프론트엔드는 WebRTC 스트림에 직결, 영상 녹화 서버는 RTSP 스트림에 직결

녹화 기능 + Cleanup 기능 (과거 영상 삭제) 필요.
Parent 1 : Children n (Recording, n: # of cameras)

Watchdog 패턴: Parent → Children 상태 체크 (Healthy?), Unhealthy 인 경우 재시작하도록.

그러면 이렇게 하면 되겠나?
```
## Answer
네, 설계가 아주 완벽하게 다듬어졌습니다. 특히 **Media Server를 스트림 허브(Proxy)**로 활용하여 카메라 부하를 1개로 고정하고, **WebRTC(실시간)**와 **RTSP(녹화)**의 목적을 명확히 분리한 점이 매우 인상적입니다.

사용자께서 정리하신 내용을 바탕으로, 실제 구현 시 참고할 만한 **구조적 확정안**을 정리해 드립니다.

## 🛠️ 확정된 컨테이너 상세 설계

### 1. Media Server (The Hub)
카메라와의 연결을 독점하고, 내부 시스템에 데이터를 분배하는 **게이트웨이**입니다.

* **Ingestion:** 카메라로부터 RTSP 스트림 수신 (단 1회 접속).
* **WebRTC Gateway:** 초저지연 실시간 뷰잉을 위해 RTSP를 WebRTC로 변환하여 프론트엔드에 송출.
* **RTSP Proxy:** 원본 영상을 변형 없이 내부 **영상 녹화 서버**로 전달.
* **Fallback:** 브라우저 환경에 따라 MSE(Media Source Extensions)나 HLS를 차선책으로 제공.

### 2. 영상 녹화 서버 (The Worker)
24/7 안정적인 기록과 저장소 관리를 담당하는 **Stateful 프로세스**입니다.

* **Data Source:** Media Server가 재송출하는 내부 RTSP 주소에 직결.
* **Recording Engine:** **FFmpeg**을 활용하여 `-c copy` 모드로 `.ts` 분할 저장 (30분/1시간 단위).
* **Process Management ($n+1$ 구조):**
    * **Parent:** 자식 프로세스들의 PID를 관리하고, 헬스체크(Heartbeat)를 수행하는 **Watchdog**.
    * **Children ($n$):** 각 카메라당 1개씩 할당된 FFmpeg 인스턴스.
* **Storage Management (Cleanup):**
    * 디스크 잔여 용량 모니터링 (예: 90% 이상 시 삭제 실행).
    * 보관 주기(Retention Policy)에 따른 오래된 `.ts` 파일 자동 삭제.

## 💡 구현을 위한 한 끗 차이 팁

1.  **Watchdog 구현:** 파이썬의 `subprocess.Popen`을 사용하면 자식 프로세스의 리턴 코드를 비차단(Non-blocking) 방식으로 확인할 수 있습니다. `poll()` 메서드가 `None`이 아니면 프로세스가 죽은 것이므로 이때 재시작 로직을 태우시면 됩니다.
2.  **Cleanup 로직:** 단순히 파일 날짜만 보는 것이 아니라, **DB의 녹화 기록 테이블과 동기화**를 맞추는 것이 중요합니다. 파일을 지운 후 DB에서도 해당 메타데이터를 제거해야 나중에 프론트엔드에서 "존재하지 않는 파일"을 호출하는 에러를 막을 수 있습니다.
3.  **저장소 계산:** $n$대의 카메라가 만드는 데이터양을 미리 계산해 보세요.
    $$\text{Total Storage (GB)} = \frac{\text{Bitrate (Mbps)} \times 3600 \times 24 \times \text{Days} \times \text{Cameras}}{8 \times 1024}$$
