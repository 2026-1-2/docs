# 2026. 05. 26. (화) (Powered by Gemini 3.1)
## Question
```
mediaMTX 에서 RTSP to WebRTC 기능만 추출하는 방법?
MediaMTX가 별도의 Custom 기능을 제공하는 것 같던데.
```
## Answer
MediaMTX에서 **RTSP to WebRTC** 기능만 분리하거나 추출하여 사용하는 방법은 사용자의 궁극적인 목적(서버 경량화 구동 vs 자체 프로그램에 소스 코드 이식)에 따라 접근 방식이 다릅니다.

먼저 질문하신 'Custom 기능'에 대한 부분을 짚고 넘어가자면, MediaMTX는 특정 프로토콜 모듈만 플러그인처럼 쉽게 뗐다 붙였다 하는(Modular) 빌드 시스템을 제공하지는 않습니다. 공식 문서에서 언급되는 커스텀 기능들은 주로 외부 인증 서버 연동, HTTP API를 통한 동적 라우팅, 그리고 `runOnReady`, `runOnDemand`와 같은 이벤트 기반 외부 스크립트(FFmpeg 등) 실행 기능을 의미합니다.

따라서 해당 기능만 떼어내어 활용하려면 다음 두 가지 방법 중 하나를 선택해야 합니다.

---

### 1. 설정 최적화를 통한 기능 격리 (가장 권장)

MediaMTX 코드를 수정하거나 재빌드할 필요 없이, 가장 쉽고 안정적으로 특정 기능만 남기는 방법입니다. `mediamtx.yml` 설정 파일에서 RTSP(입력)와 WebRTC(출력)를 제외한 모든 프로토콜 리스너를 비활성화하면, 서버는 오직 RTSP to WebRTC 전용 브릿지로만 동작하며 메모리와 CPU 리소스 소모를 최소화합니다.

* **설정 방법:** `mediamtx.yml` 파일에서 사용하지 않는 프로토콜을 모두 `no`로 변경합니다.
```yaml
# 활성화할 필수 프로토콜
rtsp: yes
webrtc: yes

# 비활성화하여 포트 점유 및 리소스 할당을 막을 프로토콜
rtmp: no
hls: no
srt: no
record: no

```



이 방식은 유지보수가 쉽고 MediaMTX의 최신 버전 업데이트를 그대로 따라갈 수 있다는 강력한 장점이 있습니다.

---

### 2. 코드 레벨 이식 (Custom Go Server 구축)

만약 개발 중인 Go 언어 기반의 백엔드 애플리케이션 내부에 "RTSP를 WebRTC로 변환하는 기능"을 소스 코드 레벨로 직접 이식(Extract)하고 싶은 것이라면, MediaMTX 프로젝트 전체를 임포트하는 것은 불필요한 라우팅 로직까지 끌고 오게 되므로 비효율적입니다.

대신, **MediaMTX가 내부적으로 핵심 엔진으로 사용하는 두 가지 오픈소스 라이브러리를 직접 조합**하여 커스텀 서버를 구축하는 것이 정석입니다.

* **RTSP 스트림 수신:** `github.com/bluenviron/gortsplib` (MediaMTX의 원작자가 만든 RTSP 전용 코어 라이브러리)
* **WebRTC 스트림 송출:** `github.com/pion/webrtc` (Go 진영의 가장 강력한 WebRTC 표준 라이브러리)

**구현 파이프라인:**

1. `gortsplib`을 사용하여 RTSP 카메라로부터 RTP 패킷(H.264 등)을 수신합니다.
2. 수신한 RTP 패킷을 파싱하여 비디오 페이로드를 추출합니다.
3. 웹 브라우저에서 요청이 오면 `pion/webrtc`를 사용해 PeerConnection을 맺고, 앞서 추출한 비디오 트랙을 WebRTC 채널로 쏴줍니다.

이 방식을 취하면 MediaMTX의 무거운 아키텍처나 yml 설정 파일 의존성 없이, 완벽하게 독립적인 나만의 "커스텀 RTSP-WebRTC 변환 모듈"을 만들 수 있습니다.

### 요약

단순히 가벼운 변환용 마이크로서비스가 필요한 것이라면 1번 방법(yml 최적화)을 적용하시고, 기존 시스템에 코드로 완전히 내재화해야 하는 상황이라면 MediaMTX 소스를 뜯어보기보다는 2번 방법(`gortsplib` + `Pion`)을 이용해 파이프라인을 직접 연결하는 것을 추천합니다.

## Question
```
다른 기능은 전혀 없이, RTSP to WebRTC 만 필요한 상황인데
mediaMTX 에서 기능을 비활성화하는게 더 낫나, 아니면 직접 만드는게 낫나?

약간의 차이라도 있으면, 더 좋은 것을 선택할것임.
```
## Answer
"약간의 차이라도 더 좋은 것을 선택하겠다"는 기준이 '극한의 리소스 다이어트'인지, 아니면 '네트워크 환경 변수에 대한 안정성'인지에 따라 승자가 완전히 갈립니다.

결론부터 말씀드리면, 리소스가 극도로 제한된 임베디드 디바이스에서 구동하는 것이 아니라면 **MediaMTX에서 설정을 비활성화(yml 튜닝)하여 사용하는 것이 압도적으로 낫습니다.**

엔지니어링 관점에서 어떤 미세한 차이가 있는지, 세 가지 핵심 지표로 비교해 드리겠습니다.

### 1. 네트워크 예외 처리와 호환성 (MediaMTX 압승)

RTSP를 읽어오는 것 자체는 코드로 쉽게 구현할 수 있습니다. 하지만 진짜 문제는 **WebRTC**입니다.

* **직접 구현 시:** WebRTC는 단순한 프로토콜이 아닙니다. 브라우저마다 미세하게 다른 SDP(Session Description Protocol) 처리, 방화벽이나 NAT(공유기) 환경을 뚫기 위한 ICE Candidate 수집 및 STUN/TURN 서버 연동 로직을 모두 직접 제어해야 합니다. 원격 환경에서 카메라의 코덱 파라미터가 조금만 틀어져도 브라우저에서 화면이 나오지 않는 현상을 디버깅해야 하는 "통신 지옥"에 빠지기 쉽습니다.
* **MediaMTX:** 이러한 WebRTC의 지저분한 엣지 케이스와 NAT 트래버절(Traversal) 처리가 이미 수많은 프로덕션 환경을 거치며 최적화되어 있습니다. 외부망 모니터링 시 발생하는 연결 끊김이나 지연 문제에 훨씬 강력합니다.

### 2. 리소스 오버헤드와 바이너리 크기 (직접 구현 승)

* **직접 구현 시:** 정확히 RTSP 수신과 WebRTC 송출 기능만 들어가므로, 컴파일된 바이너리 크기가 매우 작고 메모리 사용량을 최소화할 수 있습니다. 불필요한 라우팅 로직이나 HTTP API 서버가 돌아가지 않으므로 CPU/RAM 점유율에서 '미세하게' 더 우위를 점합니다.
* **MediaMTX:** 사용하지 않는 프로토콜(RTMP, HLS 등)을 `no`로 끄더라도, MediaMTX의 코어 라우팅 엔진과 상태 관리 로직은 메모리에 상주합니다. 다만 Golang 특성상 이 오버헤드는 수 MB 수준의 RAM과 극소량의 CPU 사이클에 불과하여, 최신 컨테이너 오케스트레이션 환경에서는 무시할 수 있는 수준입니다.

### 3. 보안 및 유지보수성 (MediaMTX 승)

* **직접 구현 시:** 코드베이스가 작아 공격 표면(Attack Surface) 자체는 줄어듭니다. 하지만 외부 라이브러리(`pion/webrtc`, `gortsplib`)에서 취약점이나 메모리 누수가 발견되었을 때, 이를 주기적으로 트래킹하고 직접 의존성을 업데이트하여 파이프라인을 재빌드해야 하는 부담이 생깁니다.
* **MediaMTX:** 활발하게 유지보수되는 오픈소스이므로, WebRTC 표준 변경이나 보안 패치에 큰 수고 없이 무임승차할 수 있습니다.

---

### 💡 최종 결론

**직접 구현을 선택해야 하는 경우:**

* 서버가 아닌 라즈베리파이 제로(Zero)나 리소스가 극도로 제한된 IoT 엣지 디바이스 내부에서 직접 구동해야 해서, 단 1MB의 메모리 오버헤드라도 허용할 수 없는 경우.

**MediaMTX 비활성화를 선택해야 하는 경우 (적극 추천):**

* Docker/Kubernetes 기반의 환경에서 구동하며, 원격 네트워크(외부 망)에서도 브라우저를 통해 안정적으로 영상 스트림을 모니터링해야 하는 경우.

WebRTC의 복잡한 시그널링 통신 및 NAT 통과 로직을 직접 구현하고 디버깅하는 데 들어가는 공수를 고려하면, **MediaMTX의 `mediamtx.yml`에서 RTSP와 WebRTC만 남기고 전부 끈 뒤 컨테이너로 띄우는 것**이 훨씬 효율적이고 "더 좋은" 선택입니다.

## Question
```
mediaMTX 공식 홈페이지(메뉴얼)을 보니까, Docker Image 를 직접 빌드해서 사용하는 경우가 있던데, 그건 뭐지?
```
## Answer
MediaMTX 공식 매뉴얼에서 제공하는 `docker build` (직접 빌드) 방식은 이미 만들어져 있는 기성품(공식 이미지) 대신 "내 입맛에 맞게 내부 환경이나 코드를 개조한 MediaMTX 컨테이너"를 만들기 위한 개발자용 옵션입니다.

일반적으로는 `docker pull bluenviron/mediamtx` 명령어로 공식 이미지를 바로 가져다 쓰면 충분하지만, 굳이 시간과 리소스를 들여 직접 빌드하는 이유는 크게 3가지입니다.

### 1. 외부 프로그램(FFmpeg) 및 하드웨어 가속 통합

MediaMTX의 유용한 기능 중 하나는 스트림이 들어올 때 외부 스크립트(`runOnReady`, `runOnDemand` 등)를 연동하는 것입니다. 이때 영상 화질이나 코덱을 변환하기 위해 FFmpeg를 가장 많이 사용합니다.

기본 MediaMTX Docker 이미지에는 FFmpeg가 포함되어 있지 않거나, 특정 GPU 하드웨어 가속(Nvidia NVENC, Intel QSV, 라즈베리파이 하드웨어 인코더 등) 드라이버가 빠져 있습니다. 따라서 **FFmpeg와 하드웨어 드라이버, 그리고 MediaMTX를 하나의 컨테이너 안에 완벽하게 묶어 넣기 위해** Dockerfile을 직접 작성하고 빌드합니다.

### 2. 소스 코드(Go) 직접 수정 및 커스텀 로직 추가

MediaMTX의 오픈소스 코드를 직접 뜯어고쳐야 하는 상황입니다.

* 사내 데이터베이스와 직접 연동되는 독자적인 보안/인증 로직 추가
* 외부 API와 통신하는 커스텀 웹훅(Webhook) 기능 구현
* 앞서 고민하셨던 것처럼 불필요한 프로토콜 엔진을 소스 코드 레벨에서 완전히 도려내어 극한으로 경량화된 버전을 만드는 경우

이처럼 원본 코드를 수정한 뒤 이를 컨테이너 환경에서 배포하려면, 당연히 공식 이미지가 아닌 로컬에서 직접 빌드(`docker build .`)하는 과정이 필수적입니다.

### 3. 보안 통제 및 베이스 이미지(Base Image) 교체

기업이나 연구실의 인프라 환경(Kubernetes 등)에서는 보안상의 이유로 외부 퍼블릭 레지스트리의 이미지를 그대로 사용하는 것을 금지하는 경우가 있습니다.

이럴 때 사내 보안팀에서 검증 완료된 안전한 리눅스(특정 버전의 Alpine이나 Ubuntu)를 베이스 이미지로 설정하고, 그 위에 MediaMTX를 직접 컴파일하여 올리기 위해 매뉴얼의 빌드 방식을 사용합니다.

### 💡 요약

단순히 `mediamtx.yml` 파일만 수정해서 RTSP to WebRTC 기능만 켜고 끌 생각이라면 **직접 빌드할 필요 없이 공식 이미지를 그대로 사용**하는 것이 가장 깔끔하고 유지보수하기 좋습니다.

하지만 추후 카메라 영상의 **코덱 변환(Transcoding)을 위해 GPU를 할당**해야 하거나, **Go 언어 소스 코드를 직접 수정하여 배포**해야 하는 상황이 온다면 그때 직접 빌드 방식을 활용하시면 됩니다.

## Question
```
내부망에서 사용할 것을 염두하고 있어서, 따로 빌드하는 과정이 필요할 것 같음.
Dockerfile 알려주기 바람.
```
## Answer
내부망(폐쇄망) 환경에서 구동하는 것을 목표로 하신다면, 불필요한 패키지를 제외하고 보안 결함을 최소화할 수 있는 **멀티 스테이지 빌드(Multi-stage Build)** 방식을 적용하는 것이 가장 이상적입니다.

소스 코드를 직접 컴파일하여 바이너리만 추출한 뒤, 초경량 이미지에 얹어 실행하는 최적화된 `Dockerfile` 구성입니다.

### 1. 프로젝트 디렉토리 구조 준비

빌드를 진행할 폴더에 다음 두 개의 파일을 같은 위치에 둡니다.

* `Dockerfile`
* `mediamtx.yml` (RTSP, WebRTC만 남긴 최소 설정 파일)

---

### 2. Dockerfile 작성

```dockerfile
# ==========================================
# Stage 1: Builder (소스 코드 컴파일)
# ==========================================
FROM golang:1.22-alpine AS builder

# Git 및 빌드 필수 패키지 설치
RUN apk add --no-cache git build-base

WORKDIR /build

# MediaMTX 소스 코드 가져오기 (가장 최신 안정화 버전 기준)
# 팁: 내부망에서 외부망 접근이 아예 차단된 상태라면, 
# 외부에서 소스 코드를 다운받아 COPY . . 방식으로 변경해야 합니다.
RUN git clone https://github.com/bluenviron/mediamtx.git .
# 특정 버전을 고정하고 싶다면 아래 주석을 해제하세요.
# RUN git checkout v1.8.2 

# CGO를 비활성화하여 완전한 정적 바이너리(Static Binary)로 컴파일
# 내부망 서버의 OS 의존성(glibc 등) 문제를 원천 차단합니다.
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o mediamtx .

# ==========================================
# Stage 2: Runtime (실행 전용 경량 이미지)
# ==========================================
# 보안을 위해 검증된 특정 버전의 Alpine Linux 사용
FROM alpine:3.19

WORKDIR /app

# 타임존 설정 및 CA 인증서 (내부망이라도 WebRTC 시그널링 등 기초 통신에 필요할 수 있음)
RUN apk add --no-cache tzdata ca-certificates

# 1단계(Builder)에서 빌드된 순수 바이너리 파일만 복사
COPY --from=builder /build/mediamtx /app/mediamtx

# 준비해둔 커스텀 최소 설정 파일 복사
COPY mediamtx.yml /app/mediamtx.yml

# 실행 권한 부여
RUN chmod +x /app/mediamtx

# RTSP TCP/UDP 포트 (8554), WebRTC API 포트 (8889), WebRTC 미디어 통신 포트 (8189)
EXPOSE 8554 8889 8189/tcp 8189/udp

# 컨테이너 시작 시 MediaMTX 및 지정된 yml 실행
ENTRYPOINT [ "/app/mediamtx", "/app/mediamtx.yml" ]

```

### 3. mediamtx.yml (최소 설정 파일)

### 4. 빌드 및 실행 방법

작성이 완료되었다면, 해당 디렉토리에서 다음 명령어를 통해 이미지를 빌드합니다.

```bash
# 1. 이미지 빌드 (태그명: custom-mediamtx)
docker build -t custom-mediamtx .

# 2. 컨테이너 백그라운드 실행
# (내부망 WebRTC 통신을 위해 호스트와 동일한 네트워크 모드를 사용하거나 포트를 정확히 매핑해야 합니다)
docker run -d \
  --name cctv-webrtc \
  -p 8554:8554 \
  -p 8889:8889 \
  -p 8189:8189/tcp \
  -p 8189:8189/udp \
  custom-mediamtx

```

이 `Dockerfile`은 빌드 완료 시 용량이 약 30MB 안팎으로 매우 작게 생성되며, Go 언어의 `CGO_ENABLED=0` 플래그 덕분에 호스트 OS의 라이브러리와 충돌할 확률이 `0`에 가깝습니다. 내부망에 배포하기 위한 가장 안전하고 확실한 구성입니다.

------------------
## Question
```
그런데, entrypoint 에 mediamtx.yml 를 왜 넣는거지?
```
## Answer
아주 예리한 질문입니다. `ENTRYPOINT [ "/app/mediamtx", "/app/mediamtx.yml" ]`에서 두 번째 인자로 설정 파일의 경로를 직접 넣은 이유는 "어떤 상황에서도 내가 만든 커스텀 설정 파일을 확실하게 물고 실행되도록 강제하는 안전장치"이기 때문입니다.

조금 더 기술적으로 설명해 드리겠습니다.

### 1. MediaMTX의 기본 동작 방식

MediaMTX 바이너리(`mediamtx`)를 인자 없이 그냥 실행하면, 프로그램은 기본적으로 자신이 실행된 현재 작업 디렉토리(Current Working Directory)에서 `mediamtx.yml` 파일을 찾으려고 시도합니다.

만약 파일을 찾지 못하면, 프로그램 내부에 하드코딩된 '전체 기능이 활성화된 기본(Default) 설정'으로 서버를 무작정 켜버립니다.

### 2. 명시적 지정이 주는 안정성 (Best Practice)

Dockerfile 위쪽에 `WORKDIR /app`을 선언했기 때문에 사실 인자를 빼고 `ENTRYPOINT [ "/app/mediamtx" ]`만 적어도 알아서 같은 폴더의 yml을 찾을 확률이 높습니다. 하지만 도커(Docker) 환경에서는 명시적으로 경로를 적어주는 것이 훨씬 안전합니다.

* **경로 혼선 방지:** 나중에 유지보수를 하면서 `WORKDIR`을 다른 곳으로 바꾸거나, 컨테이너를 실행할 때 `docker run -w` 옵션으로 실행 위치를 임의로 덮어쓰더라도 설정 파일을 잃어버리지 않습니다.
* **보안 취약점 방지 (가장 중요):** 만약 경로가 엇갈려서 커스텀 설정 파일을 찾지 못했을 때, MediaMTX가 에러를 내고 종료되는 것이 아니라 **사용하지 않는 모든 포트(RTMP, HLS 등)를 다 열어둔 채로 실행**되어 버리면 폐쇄망 환경의 보안 의도가 완전히 물거품이 됩니다.

### 요약

명령어 뒤에 설정 파일 경로(`/app/mediamtx.yml`)를 직접 던져주는 것은 "다른 곳에서 찾지 말고, 무조건 이 파일을 읽어서 실행해라. 만약 이 파일이 없으면 차라리 에러를 내고 구동을 멈춰라"라고 명확하게 지시하는 서버 운영의 모범 사례(Best Practice)라고 생각하시면 됩니다.

## Question
```
mediamtx.yml 의 옵션이 false 인 경우, 그와 관련된 옵션은 삭제해도 상관없는건가?
```
## Answer
네, **관련된 하위 옵션들은 완전히 삭제하셔도 무방합니다.** 오히려 보안과 유지보수를 위해 삭제하는 것을 적극 권장합니다.

MediaMTX(Golang 기반)는 시작 시 `mediamtx.yml` 파일을 파싱할 때, 상위 스위치(예: `rtmp: no`)가 비활성화되어 있으면 그에 종속된 세부 옵션들(`rtmpAddress`, `rtmpEncryption` 등)은 내부적으로 무시하고 넘어갑니다. 값이 적혀있든 아예 지워져 있든 동작에는 아무런 영향을 주지 않습니다.

특히 앞서 구성하신 Docker 환경처럼 목적이 뚜렷한(RTSP to WebRTC) 단일 마이크로서비스 형태라면, 불필요한 텍스트를 날려버리는 것이 구조적으로 훨씬 깔끔합니다.

### 삭제 시 얻을 수 있는 이점

* **가독성 극대화:** 수백 줄에 달하는 기본 설정 파일이 수십 줄 이내로 압축됩니다. 현재 서버가 어떤 포트를 열고 있는지 한눈에 파악할 수 있어 컨테이너 관리가 편해집니다.
* **휴먼 에러(Human Error) 방지:** 추후 설정을 만질 때, 이미 꺼져있는 기능의 하위 옵션(예: 포트 번호)을 수정해 놓고 "왜 적용이 안 되지?" 하며 디버깅에 시간을 낭비하는 실수를 원천 차단합니다.

### 💡 구성 팁 (Best Practice)

관련 하위 옵션은 과감하게 모두 지우되, **해당 프로토콜을 명시적으로 차단하겠다는 '메인 스위치' 자체는 `no`로 남겨두는 것**이 좋습니다.

**[비추천: 불필요한 설정이 남은 상태]**

```yaml
rtmp: no
rtmpAddress: :1935
rtmpEncryption: "no"
rtmpServerKey: "server.key"

```

**[추천: 최적화된 상태]**

```yaml
# 사용하지 않는 프로토콜 명시적 차단 (하위 옵션 전체 삭제)
rtmp: no
hls: no
srt: no
record: no

```

이렇게 정리해 두면, 시스템 내부에 어떤 기능이 허용되어 있고 어떤 기능이 차단되어 있는지 가장 직관적이고 확실하게 통제할 수 있습니다.

## Question
```
rtspTransports: [udp, multicast, tcp]
여기서 udp 만 활성화해도 되나?
```
## Answer
네, 설정상 `[udp]`만 남겨두는 것은 가능합니다. 하지만 실제 운영 환경(특히 CCTV/IP 카메라 연동)에서는 **`tcp`를 반드시 함께 남겨두거나, 오히려 `tcp`만 남기는 것을 강력히 권장**합니다.

MediaMTX가 카메라로부터 영상을 끌어올 때(RTSP Pull) 어떤 네트워크 통신 방식을 사용할지 결정하는 아주 중요한 옵션인데, 각각의 차이와 실무적인 파급 효과는 다음과 같습니다.

### 1. UDP (User Datagram Protocol)

* **특징:** 전송 속도가 가장 빠르고 오버헤드가 적습니다.
* **치명적인 단점 (화면 깨짐):** UDP는 패킷이 중간에 유실되어도 재전송을 요구하지 않고 그냥 무시합니다. 내부망이라 하더라도 스위치 장비의 트래픽이 몰리거나 순간적인 지연이 발생하여 영상의 핵심 프레임(I-Frame)이 유실되면, 화면 전체가 회색으로 변하거나 픽셀이 심하게 뭉개지는 현상(Smearing)이 발생합니다.

### 2. TCP (Transmission Control Protocol) - **핵심**

* **특징:** 패킷이 유실되면 다시 받아오기 때문에 영상 데이터가 100% 온전하게 전달됩니다.
* **실무 표준:** 현대의 IP 카메라와 영상 관제 시스템(VMS)은 화면 깨짐을 방지하기 위해 대부분 'RTSP over TCP' (인터리브드 모드)를 기본값으로 사용합니다. 만약 MediaMTX에서 `tcp`를 빼버리면, 오직 TCP로만 영상을 쏴주는 일부 카메라는 아예 연동조차 되지 않는 호환성 문제가 발생할 수 있습니다.

### 3. Multicast

* **특징:** 하나의 영상 소스를 내부망의 수백 대의 PC가 동시에 수신해야 할 때, 네트워크 대역폭을 아끼기 위해 사용하는 특수 브로드캐스팅 기법입니다.
* **삭제 권장:** 사내 네트워크 스위치 장비(L3)단에서 멀티캐스트 라우팅(IGMP) 설정이 완벽하게 되어 있는 특수한 환경이 아니라면 전혀 쓸 일이 없습니다. 과감히 지우셔도 됩니다.

### 💡 추천하는 설정값

현재 목표하시는 '내부망에서의 안정적인 RTSP to WebRTC' 구성을 위해서는 다음과 같이 설정하는 것이 가장 이상적입니다.

**가장 권장하는 호환성/안정성 세팅:**

```yaml
# UDP와 TCP를 모두 열어두어 카메라의 기본 설정에 유연하게 대응
rtspTransports: [udp, tcp]

```

**극한의 화질 보장 세팅 (네트워크 오버헤드 미세 증가):**

```yaml
# 화면 깨짐 현상을 원천 차단하기 위해 무조건 TCP로만 통신하도록 강제
rtspTransports: [tcp]

```

결론적으로 `multicast`는 삭제하시되, 카메라 영상의 품질 저하와 호환성 문제를 막기 위해 **`tcp`는 반드시 포함해 두는 것**이 좋습니다.
