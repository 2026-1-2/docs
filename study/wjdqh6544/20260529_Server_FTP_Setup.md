# 2026. 05. 29. (금) (Powered by Gemini 3.1)
## Question
```
OOPS: vsftpd: refusing to run with writable root inside chroot()
```
## Answer
이 에러는 `vsftpd` 서버 설정 중 사용자를 특정 폴더에 가두는 **chroot(Jail)** 기능을 사용할 때 발생하는 매우 흔하고 대표적인 보안 에러입니다.

### 🔍 원인 파악

`vsftpd`는 보안이 매우 엄격한 FTP 데몬입니다. 사용자가 다른 시스템 폴더로 넘어가지 못하게 자신의 홈 디렉토리에 가두는 설정(`chroot_local_user=YES`)을 활성화했을 때, **그 갇혀있는 최상위 폴더(홈 디렉토리)에 '쓰기(Write)' 권한이 부여되어 있으면 보안 취약점으로 간주하고 스스로 실행을 거부**합니다.

이 문제를 해결하는 데는 두 가지 방법이 있습니다. 상황에 맞게 선택해 보세요.

---

### 🛠️ 해결 방법 1: 설정 파일에서 쓰기 권한 허용 (가장 간단함)

보안 검사를 우회하여, 쓰기 권한이 있어도 그냥 접속을 허용하게 만드는 방법입니다. 특별히 보안에 극도로 민감한 서버가 아니라면 가장 빠르고 흔하게 쓰이는 방법입니다. (vsftpd 3.0 버전 이상부터 지원)

**1. vsftpd 설정 파일 열기**

```bash
sudo nano /etc/vsftpd.conf

```

*(참고: CentOS나 RHEL 계열이라면 경로가 `/etc/vsftpd/vsftpd.conf` 일 수 있습니다.)*

**2. 설정 파일 맨 아래에 다음 한 줄 추가**

```ini
allow_writeable_chroot=YES

```

*(저장하고 나가는 방법: `Ctrl + O` -> `Enter` -> `Ctrl + X`)*

**3. vsftpd 서비스 재시작**

```bash
sudo systemctl restart vsftpd

```

---

### 🛠️ 해결 방법 2: 폴더 권한 구조 변경 (가장 안전함)

`vsftpd`가 의도한 보안 원칙을 그대로 따르는 방법입니다. 최상위 홈 디렉토리의 쓰기 권한은 뺏고, 대신 그 안에 파일을 업로드할 수 있는 '하위 폴더'를 따로 만들어주는 방식입니다.

**1. 접속하려는 FTP 사용자의 홈 디렉토리 쓰기 권한 제거**

```bash
sudo chmod a-w /home/사용자계정

```

*(이제 이 사용자는 최상위 폴더에는 파일을 직접 올릴 수 없습니다.)*

**2. 파일을 업로드할 별도의 하위 디렉토리 생성**

```bash
sudo mkdir /home/사용자계정/uploads

```

**3. 생성한 하위 디렉토리의 소유권 설정**

```bash
sudo chown 사용자계정:사용자계정 /home/사용자계정/uploads

```

**4. vsftpd 서비스 재시작**

```bash
sudo systemctl restart vsftpd

```

이제 FTP 클라이언트로 다시 접속해 보시면 `OOPS` 에러 없이 정상적으로 로그인이 되실 겁니다! 방법 2를 선택하셨다면 파일을 올릴 때 반드시 `uploads` 폴더 안으로 들어가서 올려야 합니다.

## Question
```
ftp 저장 경로 바꾸기
```
## Answer
현재 사용 중이신 **`vsftpd`** 서버에서 FTP 접속 시 기본으로 연결되는 저장 경로(폴더)를 변경하는 방법은 크게 두 가지가 있습니다. 상황에 맞는 방법을 선택해 보세요.

---

### 방법 1: `vsftpd` 설정 파일에서 경로 강제 지정 (추천)

서버의 계정 정보는 그대로 두되, FTP 접속 시에만 특정 폴더(예: `/var/ftp/data`)로 연결되게 만드는 가장 깔끔한 방법입니다.

**1. 새로운 저장 폴더 만들기 (이미 있다면 생략)**

```bash
sudo mkdir -p /원하는/새로운/경로

```

*(예: `sudo mkdir -p /var/ftp/data`)*

**2. 폴더 소유권 변경**
FTP로 접속하는 사용자가 파일에 읽고 쓸 수 있도록 권한을 줍니다.

```bash
sudo chown 사용자계정:사용자계정 /원하는/새로운/경로

```

**3. vsftpd 설정 파일 수정**

```bash
sudo nano /etc/vsftpd.conf

```

**4. 설정 파일 맨 아래에 다음 내용 추가**

```ini
local_root=/원하는/새로운/경로

```

*(만약 모든 사용자가 각자의 폴더로 가게 하려면 이 방법 대신 아래 '방법 2'를 쓰셔야 합니다. 이 설정은 접속하는 모든 사용자를 저 경로로 보냅니다.)*

**5. 서비스 재시작**

```bash
sudo systemctl restart vsftpd

```

---

### 방법 2: 사용자의 '홈 디렉토리' 자체를 변경 (특정 사용자만 바꿀 때)

리눅스 시스템에서 해당 계정의 기본 집(Home) 주소 자체를 바꿔버리는 방법입니다. 사용자가 여러 명이고, 특정 계정의 저장 위치만 바꾸고 싶을 때 사용합니다.

**1. 폴더 생성 및 권한 부여 (위와 동일)**

```bash
sudo mkdir -p /원하는/새로운/경로
sudo chown 사용자계정:사용자계정 /원하는/새로운/경로

```

**2. 계정의 홈 디렉토리 변경**

```bash
sudo usermod -d /원하는/새로운/경로 사용자계정

```

**3. 서비스 재시작**

```bash
sudo systemctl restart vsftpd

```

### 🚨 주의사항 (이전에 발생했던 OOPS 에러 관련)

경로를 바꾸시더라도, 앞서 겪으셨던 **`chroot` 보안 규칙**은 똑같이 적용됩니다.

만약 설정 파일(`/etc/vsftpd.conf`)에 `allow_writeable_chroot=YES`를 추가해 두셨다면 상관없지만, 그렇지 않다면 새로 지정한 최상위 경로에도 쓰기 권한이 없어야 접속이 가능(OOPS 에러 방지)합니다.

따라서 가장 안전한 구조는 다음과 같이 폴더를 한 뎁스 더 나누는 것입니다.

* 접속 시 떨어지는 기본 경로: `/var/ftp/data` (쓰기 권한 없애기 `chmod a-w`)
* 실제 파일 업로드용 경로: `/var/ftp/data/uploads` (쓰기 권한 부여)

## Question
```
경로를 바꾸니까 username is invalid 가 뜨는데?
```
## Answer
경로를 변경한 직후에 'username is invalid' 또는 '530 Login incorrect' 같은 로그인 오류가 발생하는 것은, 계정 자체가 삭제된 것이 아니라 **리눅스 보안 시스템이나 FTP 데몬이 새로운 경로에 접근할 수 없어 로그인을 원천 차단**했기 때문입니다.

가장 유력한 원인과 해결 방법을 순서대로 확인해 보시기 바랍니다.

### 1. 상위 폴더의 '통과(실행)' 권한 부족 (가장 흔함)

리눅스에서는 최종 폴더의 권한이 열려 있더라도, 그 폴더로 가는 **중간 경로(상위 폴더)들이 막혀 있으면 접근할 수 없습니다.** 예를 들어 새로운 경로를 `/var/ftp/data`로 하셨다면, `/var`와 `/var/ftp` 폴더에도 외부 접근 권한이 있어야 합니다.

* **해결 방법:** 새로운 경로의 상위 폴더들에 최소한의 읽기/실행 권한(755)이 있는지 확인하고 부여합니다.
```bash
sudo chmod 755 /새로운경로의/상위폴더
sudo chmod 755 /새로운경로의/최종폴더

```



### 2. 폴더가 실제로 존재하지 않거나 오타가 난 경우

앞서 `usermod -d` 명령어를 통해 사용자의 홈 디렉토리를 변경하는 방식을 사용하셨다면, 폴더를 미리 생성하지 않았거나 명령어 입력 중 오타가 발생했을 수 있습니다. 홈 디렉토리가 존재하지 않으면 로그인이 거부됩니다.

* **확인 방법:** 계정 정보 파일에서 경로가 정확히 바뀌었는지 확인합니다.
```bash
cat /etc/passwd | grep 사용자계정

```


출력된 결과의 끝부분에 지정하신 경로가 정확히 들어있는지, 그리고 해당 경로에 실제로 폴더가 존재하는지(`ls -l /설정한/경로`) 확인해 보세요.

### 3. SELinux 보안 정책 차단 (CentOS, RHEL, Rocky Linux인 경우)

현재 사용 중인 서버가 우분투가 아니라 CentOS 계열이라면, 기본 보안 모듈인 SELinux가 켜져 있을 확률이 높습니다. SELinux는 사용자가 기본 홈 디렉토리(`/home/...`)가 아닌 임의의 다른 폴더로 FTP 접속을 시도하면 해킹으로 간주하고 즉시 차단합니다.

* **해결 방법:** SELinux 설정에서 FTP가 모든 경로에 접근할 수 있도록 허용해 주어야 합니다.
```bash
sudo setsebool -P allow_ftpd_full_access 1

```


*(만약 우분투(Ubuntu)를 사용 중이시라면 이 단계는 무시하셔도 됩니다.)*

## Question
```
디렉토리를 생성할 때 rxrxrx 로 생성이 되는데
이거 rwxrwxrwx 로 생성되게 할 수 없나?
```
## Answer
네, 가능합니다! 리눅스에서 파일이나 디렉토리를 새로 생성할 때 기본 권한(퍼미션)을 결정하는 것은 `umask`라는 시스템 설정입니다.

현재 디렉토리가 `r-xr-xr-x` (숫자로 555)로 생성된다면, 현재 접속하신 쉘의 `umask` 값이 `0222`로 설정되어 있을 확률이 높습니다. (기본 최대 권한인 `777`에서 `umask` 값 `222`를 뺀 값이 생성 권한이 됩니다.)

디렉토리가 항상 `rwxrwxrwx` (777)로 생성되게 하려면 이 `umask` 값을 `0000`으로 변경해 주시면 됩니다.

### 설정 방법

**1. 일시적 적용 (현재 켜져 있는 터미널에서만)**
터미널에 아래 명령어를 입력하시면, 창을 닫기 전까지 생성되는 모든 디렉토리가 777로 만들어집니다.

```bash
umask 0000

```

**2. 영구적 적용 (재부팅이나 재접속 후에도 유지)**
매번 설정하기 번거롭다면, 사용 중인 계정의 쉘 설정 파일(주로 `~/.bashrc` 또는 `~/.zshrc`)에 해당 값을 고정해 주어야 합니다.

터미널에 아래 명령어를 차례대로 입력하세요.

```bash
echo "umask 0000" >> ~/.bashrc
source ~/.bashrc

```

### 🚨 시스템 및 보안 주의사항

설정 방법은 위와 같이 매우 간단하지만, **모든 디렉토리를 기본적으로 777(`rwxrwxrwx`)로 생성하게 만드는 것은 시스템 운영상 강력히 비추천합니다.**

777 권한은 해당 시스템에 접속할 수 있는 '아무나(Other)'가 해당 폴더 안에 들어와서 파일을 지우거나, 덮어쓰거나, 새로운 실행 파일을 만들 수 있다는 뜻입니다. 특히 시스템 레벨의 취약점을 분석하고 다양한 CVE를 재현하는 등의 연구를 진행하는 환경에서는, 777 권한이 열려 있는 디렉토리가 의도치 않은 권한 상승(Privilege Escalation) 공격의 손쉬운 타겟이 되거나 악의적인 페이로드가 은닉되는 등 시스템 자체가 심각하게 오염될 위험이 있습니다.

따라서 기본 `umask` 값은 보편적이고 안전한 **`0022`** (디렉토리 755: `rwxr-xr-x`)로 유지하시고, 777 권한이 필요한 특정 테스트용 디렉토리만 생성하신 후에 `chmod 777 폴더명` 명령어로 개별 변경하여 사용하시는 것을 강력히 권장합니다.

## Question
```
ftp 에서 디렉토리를 생성하는 상황임.

local_umask=0777

이렇게 하면 되나? 왜 d---------- 으로 뜨지?
```
## Answer
**`umask` 설정에 대한 아주 흔한 오해**를 겪으셨군요! `d----------` 로 뜨는 것은 오류가 아니라, 설정하신 값에 따라 리눅스가 정확하게 계산한 결과입니다.

### 🔍 원인: umask는 권한을 '주는' 것이 아니라 '빼는' 것입니다

`umask` (User Mask)의 개념은 "이 권한을 부여해라"가 아니라, "기본 권한에서 이 값만큼 빼고 만들어라"입니다.

리눅스에서 디렉토리(폴더)를 생성할 때 주어지는 최대 기본 권한은 `777`(`rwxrwxrwx`)입니다.
여기서 설정하신 `0777`이라는 umask 값을 빼면 다음과 같은 계산이 나옵니다.

* **기본 권한:** `777` (`rwxrwxrwx`)
* **설정한 umask:** `- 777`
* **최종 생성 권한:** `= 000` (`d----------`, 즉 아무도 읽고 쓰고 실행할 수 없음)

이 때문에 모든 권한이 다 깎여서 빈 껍데기만 만들어진 것입니다.

---

### 🛠️ 올바른 설정 방법

FTP(`vsftpd`)를 통해 디렉토리를 생성할 때 `777`(`rwxrwxrwx`) 권한으로 만들어지게 하려면, **아무 권한도 빼지 말라**고 설정해야 합니다. 즉, umask 값을 `000`으로 주셔야 합니다.

**1. 설정 파일 수정**

```bash
sudo nano /etc/vsftpd.conf

```

**2. local_umask 값 변경**

```ini
local_umask=000

```

*(777 - 000 = 777이 되므로 `rwxrwxrwx`로 생성됩니다.)*

**3. 서비스 재시작**

```bash
sudo systemctl restart vsftpd

```

### 💡 추가 정보: 업로드되는 '파일'의 권한

`local_umask=000`으로 설정하시면 디렉토리(폴더)는 `777`(`rwxrwxrwx`)로 정상 생성됩니다.

하지만 폴더가 아닌 **일반 파일(.txt, .png 등)을 업로드할 때는 `666`(`rw-rw-rw-`)으로 생성**됩니다. 왜냐하면 리눅스는 보안상 일반 파일이 생성될 때 실행 권한(`x`)을 기본적으로 주지 않기 때문에, 파일의 최대 기본 권한이 `666`에서 시작하기 때문입니다. (666 - 000 = 666)

### 🚨 보안 재강조

이전에도 말씀드렸지만, FTP 환경에서 접속하는 사용자가 만드는 모든 폴더가 `777`로 생성되는 것은 **다른 FTP 사용자나 시스템 접속자가 해당 폴더를 마음대로 지우거나 변조할 수 있음**을 의미합니다. 테스트나 연구 목적이 끝난 후, 실제 서비스 환경에서는 기본값인 `local_umask=022` (디렉토리 755, 파일 644)로 되돌리시는 것을 강력히 권장합니다.
