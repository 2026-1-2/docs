# Docker 네트워크와 볼륨 심화 관리

## 1. 개요

버티포트 CCTV 감시 시스템은 MediaMTX, NestJS API 서버, MySQL, 녹화 서버 등 다수의 컨테이너가 협업한다.
컨테이너 간 통신을 위한 네트워크 설계와 영상 녹화 파일의 영속적 저장을 위한 볼륨 전략은
시스템 안정성과 데이터 무결성에 직결된다. 본 문서에서는 Docker 네트워크 드라이버와 볼륨 유형을 심화 학습한다.

---

## 2. Docker 네트워크 드라이버

Docker는 4가지 기본 네트워크 드라이버를 제공한다.

| 드라이버 | 설명 | 격리 수준 | 사용 사례 |
|----------|------|-----------|-----------|
| `bridge` | 기본 드라이버. 가상 브리지를 통한 컨테이너 간 통신 | 중간 | 단일 호스트의 컨테이너 간 통신 |
| `host` | 호스트의 네트워크 스택을 직접 사용 | 없음 | 높은 네트워크 성능이 필요한 경우 |
| `overlay` | 여러 Docker 호스트를 연결하는 분산 네트워크 | 높음 | Docker Swarm 멀티 호스트 환경 |
| `none` | 네트워크를 완전히 비활성화 | 최대 | 보안이 중요한 격리 컨테이너 |

### 2-1. bridge 드라이버 상세

기본 bridge(`docker0`)와 사용자 정의 bridge는 동작 방식이 다르다.

```bash
# 기본 bridge 네트워크 확인
docker network inspect bridge

# 사용자 정의 bridge 네트워크 생성
docker network create --driver bridge mmp-network
```

| 항목 | 기본 bridge | 사용자 정의 bridge |
|------|-------------|-------------------|
| DNS 해석 | 불가 (IP로만 통신) | 컨테이너 이름으로 DNS 해석 가능 |
| 자동 연결 | 모든 컨테이너 자동 연결 | 명시적으로 연결해야 함 |
| 격리 | 모든 컨테이너가 같은 네트워크 | 네트워크별로 격리 |
| 환경 변수 공유 | `--link` 필요 (deprecated) | 불필요 |

### 2-2. 컨테이너 간 DNS 통신

사용자 정의 네트워크에서는 서비스 이름이 곧 호스트명이 된다.

```bash
# mmp-network에 컨테이너 연결
docker run -d --name mysql --network mmp-network mysql:8.0
docker run -d --name mmp-server --network mmp-network mmp-server:latest

# mmp-server 내부에서 mysql에 접근
# mysql:3306 으로 직접 접근 가능 (DNS 자동 해석)
```

```
┌─────────────────── mmp-network (bridge) ───────────────────┐
│                                                             │
│  ┌───────────┐    DNS 해석     ┌──────────┐                │
│  │ mmp-server│ ──────────────→ │  mysql   │                │
│  │ :3000     │   mysql:3306    │  :3306   │                │
│  └───────────┘                 └──────────┘                │
│                                                             │
│  ┌───────────┐                 ┌───────────────┐           │
│  │ mediamtx  │                 │ video-recorder│           │
│  │ :8554     │                 │               │           │
│  └───────────┘                 └───────────────┘           │
└─────────────────────────────────────────────────────────────┘
```

### 2-3. host 드라이버 활용

MediaMTX는 RTSP(TCP)와 WebRTC(UDP) 포트를 대량으로 사용한다.
`host` 네트워크를 사용하면 포트 매핑 오버헤드를 제거하고 UDP 성능을 극대화할 수 있다.

```yaml
# docker-compose.yml
mediamtx:
  image: bluenviron/mediamtx:latest
  network_mode: host   # 호스트 네트워크 직접 사용
  volumes:
    - ./mediamtx.yml:/mediamtx.yml
```

> **주의**: `host` 모드에서는 `ports` 매핑이 무시되며, 호스트의 포트와 직접 충돌할 수 있다.

## 3. Docker 볼륨 종류

Docker는 3가지 데이터 저장 방식을 제공한다.

| 유형 | 저장 위치 | 관리 주체 | 사용 사례 |
|------|-----------|-----------|-----------|
| Named Volume | `/var/lib/docker/volumes/` | Docker Engine | DB 데이터, 영속 데이터 |
| Bind Mount | 호스트의 지정 경로 | 사용자 | 설정 파일, 소스 코드, 녹화 파일 |
| tmpfs | 메모리 (RAM) | OS | 임시 데이터, 민감 정보 |

### 3-1. Named Volume

Docker가 자체적으로 관리하는 볼륨이다. 컨테이너가 삭제되어도 데이터가 보존된다.

```bash
# 볼륨 생성
docker volume create mysql_data

# 볼륨 목록 확인
docker volume ls

# 볼륨 상세 정보
docker volume inspect mysql_data
# 출력 예시:
# "Mountpoint": "/var/lib/docker/volumes/mysql_data/_data"

# 사용하지 않는 볼륨 정리
docker volume prune
```

### 3-2. Bind Mount

호스트의 특정 디렉토리를 컨테이너 내부에 마운트한다.

```bash
# 절대 경로로 바인드 마운트
docker run -v /host/path/recordings:/app/recordings video-recorder

# 읽기 전용 마운트 (설정 파일 보호)
docker run -v ./mediamtx.yml:/mediamtx.yml:ro mediamtx
```

### 3-3. tmpfs 마운트

메모리에 임시 파일시스템을 생성한다. 컨테이너 종료 시 데이터가 즉시 삭제된다.

```yaml
services:
  mmp-server:
    tmpfs:
      - /tmp:size=100M   # 임시 파일용 RAM 디스크 (100MB 제한)
```

## 4. 볼륨 백업과 복원

### 4-1. Named Volume 백업

```bash
# mysql_data 볼륨을 tar로 백업
docker run --rm \
  -v mysql_data:/source:ro \
  -v $(pwd)/backup:/backup \
  alpine tar czf /backup/mysql_data_backup.tar.gz -C /source .

# 백업 파일 확인
ls -lh backup/mysql_data_backup.tar.gz
```

### 4-2. 볼륨 복원

```bash
# 새 볼륨 생성 후 백업 데이터 복원
docker volume create mysql_data_restored

docker run --rm \
  -v mysql_data_restored:/target \
  -v $(pwd)/backup:/backup \
  alpine tar xzf /backup/mysql_data_backup.tar.gz -C /target
```

### 4-3. MySQL 전용 백업 (mysqldump)

```bash
# 실행 중인 MySQL 컨테이너에서 논리적 백업
docker exec mysql mysqldump -u root -p${DB_ROOT_PASSWORD} mmp_db \
  > backup/mmp_db_$(date +%Y%m%d).sql

# 복원
docker exec -i mysql mysql -u root -p${DB_ROOT_PASSWORD} mmp_db \
  < backup/mmp_db_20260429.sql
```

## 5. docker-compose.yml 네트워크/볼륨 설정

프로젝트의 실제 구성을 반영한 docker-compose.yml 예시이다.

```yaml
version: '3.8'

services:
  mysql:
    image: mysql:8.0
    networks:
      - backend
    volumes:
      - mysql_data:/var/lib/mysql
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_ROOT_PASSWORD}
      MYSQL_DATABASE: mmp_db

  mmp-server:
    build: ./mmp-server
    networks:
      - backend
      - frontend
    depends_on:
      mysql:
        condition: service_healthy
    environment:
      DATABASE_URL: mysql://root:${DB_ROOT_PASSWORD}@mysql:3306/mmp_db

  mediamtx:
    image: bluenviron/mediamtx:latest
    networks:
      - backend
      - frontend
    volumes:
      - ./mediamtx.yml:/mediamtx.yml:ro
    ports:
      - "8554:8554"     # RTSP
      - "8889:8889"     # WebRTC HTTP
      - "8189:8189/udp" # WebRTC UDP

  video-recorder:
    build: ./video-recorder
    networks:
      - backend
    volumes:
      - recordings:/app/recordings   # Named Volume
      - ./recorder-config:/app/config:ro

networks:
  backend:
    driver: bridge    # 서버-DB-미디어 내부 통신
  frontend:
    driver: bridge    # 클라이언트 접근 가능한 서비스

volumes:
  mysql_data:
    driver: local
  recordings:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /data/recordings   # 호스트의 대용량 스토리지 경로
```

### 네트워크 분리 전략

```
┌─────────── frontend 네트워크 ────────────┐
│  client ←→ mmp-server ←→ mediamtx       │
└──────────────────────────────────────────┘
                  │
┌─────────── backend 네트워크 ─────────────┐
│  mmp-server ←→ mysql                     │
│  mmp-server ←→ mediamtx                  │
│  video-recorder ←→ mediamtx              │
└──────────────────────────────────────────┘
```

- `frontend`: 외부 클라이언트가 접근할 수 있는 서비스만 포함
- `backend`: DB, 녹화 서버 등 내부 통신 전용 (외부 접근 차단)

## 6. 프로젝트 녹화 파일 볼륨 전략

버티포트 CCTV 시스템에서 녹화 파일은 지속적으로 생성되므로 스토리지 전략이 중요하다.

| 항목 | 전략 |
|------|------|
| 저장 위치 | Named Volume + 호스트 바인드 (`/data/recordings`) |
| 디렉토리 구조 | `/recordings/{camera_id}/{YYYY-MM-DD}/{HH-MM-SS}.mp4` |
| 보존 기간 | 30일 (cron으로 오래된 파일 자동 삭제) |
| 디스크 모니터링 | `df -h` 기반 알림 (80% 초과 시 경고) |
| 백업 | 일간 증분 백업 → 외부 스토리지 |

```bash
# 녹화 파일 정리 스크립트 (30일 이상 된 파일 삭제)
#!/bin/bash
find /data/recordings -name "*.mp4" -mtime +30 -delete
find /data/recordings -type d -empty -delete
echo "[$(date)] Cleanup completed" >> /var/log/recording-cleanup.log
```

## 7. 디버깅 명령어

```bash
# 네트워크에 연결된 컨테이너 확인
docker network inspect mmp-network --format '{{range .Containers}}{{.Name}} {{end}}'

# 컨테이너 내부에서 네트워크 테스트
docker exec mmp-server ping mysql
docker exec mmp-server nslookup mediamtx

# 볼륨 사용량 확인
docker system df -v

# 특정 볼륨의 실제 디스크 사용량
du -sh /var/lib/docker/volumes/mysql_data/_data

# 컨테이너의 마운트 정보 확인
docker inspect --format '{{json .Mounts}}' mmp-server | jq
```

## 8. 정리

- 사용자 정의 bridge 네트워크를 사용하면 서비스 이름 기반 DNS 해석이 가능하여 IP 하드코딩을 피할 수 있다
- 네트워크를 frontend/backend로 분리하면 DB가 외부에 노출되는 것을 방지한다
- Named Volume은 Docker가 관리하므로 데이터 영속성이 보장되며, DB 저장에 적합하다
- 녹화 파일처럼 호스트에서 직접 접근해야 하는 데이터는 Bind Mount를 사용한다
- 볼륨 백업은 tar 아카이브 또는 mysqldump를 통해 정기적으로 수행해야 한다
- MediaMTX의 WebRTC UDP 트래픽은 host 네트워크 모드를 고려할 수 있다
