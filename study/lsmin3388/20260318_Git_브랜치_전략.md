# Git 브랜치 전략

## 학습 일자
2026.03.18

## 개요
버티포트 CCTV 감시 시스템은 React, NestJS, Docker/MediaMTX 등 다수 컴포넌트로 구성되며 4~5명이 동시 개발한다. 체계적인 브랜치 전략으로 코드 충돌을 최소화하고 안정적인 배포 파이프라인을 유지하고자 한다.

---

## 1. Git Flow vs GitHub Flow 비교

| 항목 | Git Flow | GitHub Flow |
|------|----------|-------------|
| 브랜치 수 | main, develop, feature, release, hotfix | main, feature |
| 복잡도 | 높음 (5종 브랜치) | 낮음 (2종 브랜치) |
| 배포 주기 | 릴리즈 단위 | 지속적 배포(CD) |
| 적합 환경 | 버전 관리 필요 제품 | 웹 서비스, SaaS |
| hotfix | hotfix 브랜치 분리 | main에서 직접 분기 |

## 2. 프로젝트 적용 브랜치 전략

**GitHub Flow 기반 변형 전략** 채택. `dev` 브랜치를 스테이징 용도로 활용한다.

| 브랜치 | 용도 | 보호 정책 |
|--------|------|-----------|
| `main` | 프로덕션 배포 코드 | PR 필수, 1명 이상 리뷰 |
| `dev` | 개발 통합 및 테스트 | PR 필수 |
| `feat/<기능명>` | 기능 개발 | 자유 push |
| `fix/<버그명>` | 버그 수정 | 자유 push |

### 개발 플로우

```bash
# 1. dev에서 feature 브랜치 생성
git checkout dev && git pull origin dev
git checkout -b feat/camera-streaming

# 2. 기능 개발 및 커밋
git add src/camera/
git commit -m "feat(camera): RTSP 스트림 수신 모듈 구현"

# 3. push 후 PR 생성 (feat → dev)
git push origin feat/camera-streaming

# 4. 코드 리뷰 → Squash Merge → dev에서 테스트 → dev → main PR
```

## 3. 커밋 메시지 컨벤션 (Conventional Commits)

### 형식

```
<type>(<scope>): <subject>
```

### 타입 정의

| 타입 | 설명 | 예시 |
|------|------|------|
| `feat` | 새 기능 추가 | feat(auth): JWT 로그인 구현 |
| `fix` | 버그 수정 | fix(stream): HLS 세그먼트 누락 해결 |
| `docs` | 문서 변경 | docs(api): Swagger 명세 업데이트 |
| `refactor` | 리팩토링 | refactor(camera): 서비스 레이어 분리 |
| `chore` | 빌드/설정 | chore: Docker Compose 포트 수정 |
| `test` | 테스트 코드 | test(auth): 로그인 단위 테스트 추가 |
| `ci` | CI/CD 설정 | ci: GitHub Actions 워크플로우 추가 |

```bash
# 좋은 예시
git commit -m "feat(camera): Hikvision RTSP 스트림 연결 모듈 구현

- RTSP URL 파싱 및 검증 로직 추가
- 연결 실패 시 3회 재시도 로직 구현
Refs: #42"

# 나쁜 예시
git commit -m "카메라 수정"
```

## 4. PR 규칙 및 머지 전략

### PR 템플릿

```markdown
## 변경 사항
- [ ] 기능 추가 / 버그 수정 / 리팩토링

## 설명
<!-- 변경 내용을 상세히 기술 -->

## 테스트
- [ ] 로컬 테스트 완료
- [ ] Docker 환경 테스트 완료

## 관련 이슈
- closes #이슈번호
```

### 머지 전략

| 전략 | 설명 | 사용 시점 |
|------|------|-----------|
| Squash Merge | 여러 커밋을 하나로 합침 | feat → dev (기본) |
| Merge Commit | 머지 커밋 생성 | dev → main |

```bash
gh pr merge 15 --squash --delete-branch
```

## 5. Merge vs Rebase

```bash
# Merge: 머지 커밋이 생성됨
git checkout feat/camera-streaming
git merge dev

# Rebase: 선형 히스토리로 재배치
git checkout feat/camera-streaming
git rebase dev
```

| 상황 | 전략 | 이유 |
|------|------|------|
| feat → dev | Squash Merge | 깔끔한 히스토리 유지 |
| dev → main | Merge Commit | 통합 이력 보존 |
| dev 최신화 (로컬) | `git pull --rebase` | 불필요한 머지 커밋 방지 |

## 6. Conflict 해결 방법

```bash
# 1. 충돌 발생
git merge dev
# CONFLICT (content): Merge conflict in src/camera/camera.service.ts
```

```typescript
// 충돌 마커 해석
<<<<<<< HEAD (현재 브랜치)
const RTSP_TIMEOUT = 10000;
=======
const RTSP_TIMEOUT = 15000;
>>>>>>> dev (병합 대상 브랜치)
```

```bash
# 해결 순서: 마커 제거 → 코드 선택 → 스테이징 → 커밋
git add src/camera/camera.service.ts
git commit -m "merge: dev를 feat/camera-streaming에 병합 (충돌 해결)"
```

VSCode 충돌 해결 옵션: Accept Current / Accept Incoming / Accept Both / Compare Changes

## 7. .gitignore 설정

```gitignore
# Node.js
node_modules/
dist/
*.log

# 환경 변수
.env
.env.local

# IDE / OS
.vscode/
.idea/
.DS_Store

# Docker
docker-compose.override.yml

# 영상 파일 (CCTV 녹화본)
recordings/
*.mp4
*.ts
*.m3u8

# Prisma
prisma/migrations/**/migration_lock.toml

# 테스트 커버리지
coverage/
```

```bash
# 이미 추적 중인 파일을 .gitignore에 추가한 경우
git rm -r --cached .
git add .
git commit -m "chore: .gitignore 갱신 및 캐시 초기화"
```
