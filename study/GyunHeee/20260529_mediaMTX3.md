## MediaMTX를 위한 별도 레포가 필요한가?

**결론: 별도 레포 없이 기존 레포 내 설정 파일로 관리하는 것이 일반적이며, 본 프로젝트도 이 방식을 따른다.**

### 이유

MediaMTX는 자체 애플리케이션 코드를 작성하는 컴포넌트가 아니라, **공식 Docker 이미지(`bluenviron/mediamtx`)를 그대로 사용하고 설정 파일(`mediamtx.yml`)만 주입하는 구조**다. 즉 빌드 대상이 되는 소스 코드가 없기 때문에, `video-recorder`나 `mmp-server`처럼 별도의 코드 레포를 둘 이유가 약하다.

| 비교 항목 | video-recorder / mmp-server | MediaMTX |
|---|---|---|
| 소스 코드 보유 | O (직접 개발) | X (공식 이미지 사용) |
| 빌드 필요 여부 | O (CI에서 빌드) | X (이미지 pull만) |
| 버전 관리 대상 | 애플리케이션 코드 | 설정 파일(`mediamtx.yml`)만 |
| 레포 분리 필요성 | 높음 | 낮음 |

### 권장 구조

MediaMTX 관련 설정은 다음 중 하나의 방식으로 관리하는 것이 적절하다.

1. **mmp-server 레포 내 `infra/` 또는 `docker/` 디렉토리에 포함**
   - `mmp-server`가 MediaMTX의 REST API를 호출하며 가장 강하게 결합되어 있으므로, 같은 레포에서 `mediamtx.yml`과 `docker-compose.yml`을 함께 관리하면 배포 시점의 정합성을 맞추기 쉽다.
2. **별도의 `infra` 또는 `deploy` 레포로 분리**
   - `docker-compose.yml`, `mediamtx.yml`, Caddy 설정, `run.sh` 등 인프라 관련 파일을 한 곳에 모아 관리하는 방식. 배포 파이프라인(CD)이 이 레포를 기준으로 동작하게 하면 코드 레포와 배포 설정을 분리할 수 있다.

### 본 프로젝트 적용 시 고려사항

- 현재 3개 레포(`video-recorder`, `mmp-server`, `client`) 구조에 MediaMTX용 코드 레포를 **추가로 만들 필요는 없다.**
- 다만 `mediamtx.yml` 설정 파일과 `docker-compose.yml`이 현재 어느 레포에 위치하는지는 명확히 문서화해 두는 것이 좋다. (예: README의 "배포 구조" 섹션에 "MediaMTX 설정은 `mmp-server/infra/mediamtx.yml`에서 관리" 같이 명시)
- 보고서/발표 자료에서는 "3개 레포 + 설정 기반 인프라 컴포넌트(MediaMTX, Caddy)"로 구분해서 설명하면, 왜 레포가 3개뿐인지에 대한 질문에도 명확히 답할 수 있다.
