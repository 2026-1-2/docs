# 프롬프트

> 현재 우리가 `RTSP`, `HLS`, `WebRTC`를 어떤 기준으로 이해하고 선택해야 하는지 정리해 줘.

# RTSP, HLS, WebRTC 비교와 프로젝트 선택 기준

## 1. 먼저 결론부터

`RTSP`와 `HLS.js`는 서로 같은 계층의 기술이 아닙니다.

- `RTSP`는 **카메라나 미디어 서버가 영상을 주고받을 때 사용하는 스트리밍 프로토콜**
- `HLS.js`는 **브라우저에서 HLS 영상을 재생하기 위해 사용하는 JavaScript 라이브러리**

즉, 둘은 경쟁 관계라기보다 보통 아래처럼 함께 등장합니다.

```text
카메라 -> RTSP -> 서버 -> HLS(.m3u8, .ts) -> 브라우저(hls.js)
```

---

## 2. RTSP란?

`RTSP (Real-Time Streaming Protocol)`는 주로 IP 카메라, CCTV, NVR, 미디어 서버 환경에서 많이 쓰이는 실시간 스트리밍 프로토콜입니다.

카메라가 서버로 영상을 보내거나, 서버가 카메라 스트림을 받아올 때 자주 사용됩니다.

### 특징

- 저지연 실시간 스트리밍에 적합
- IP 카메라, CCTV 장비에서 널리 지원
- 보통 H.264, H.265 같은 코덱과 함께 사용
- 주로 `rtsp://...` 형태의 주소를 사용

### 장점

- 지연 시간이 짧아 관제 시스템에 유리
- 카메라 장비 호환성이 좋음
- 서버에서 녹화, 분석, 중계 파이프라인을 만들기 좋음

### 단점

- 웹 브라우저가 RTSP를 기본 지원하지 않음
- 그대로 프론트엔드에서 재생하기 어려움
- 네트워크, 포트, 방화벽 이슈에 민감할 수 있음

---

## 3. HLS와 HLS.js란?

### HLS란?

`HLS (HTTP Live Streaming)`는 Apple이 만든 HTTP 기반 스트리밍 방식입니다.

영상을 잘게 쪼갠 세그먼트 파일(`.ts`, 최근에는 fMP4도 사용)과 재생 목록 파일(`.m3u8`)로 전달합니다.

브라우저나 플레이어는 이 목록을 읽으면서 순차적으로 영상을 재생합니다.

### HLS.js란?

`hls.js`는 브라우저가 HLS를 직접 재생하지 못하는 경우, JavaScript로 `m3u8`과 세그먼트를 읽어서 `<video>` 태그에 붙여 재생해 주는 라이브러리입니다.

즉, `hls.js`는 영상 프로토콜이 아니라 **브라우저 재생 도구**입니다.

### 특징

- HTTP 기반이라 웹 배포와 연동이 쉬움
- 브라우저 친화적
- CDN, 캐시, 인증 처리와 잘 맞음
- 다만 세그먼트 기반이라 RTSP보다 지연이 큼

### 장점

- 웹 브라우저에서 다루기 쉽다
- 프론트엔드에서 `<video>`와 함께 붙이기 쉽다
- 네트워크 환경이 비교적 안정적이다
- 대규모 배포, 중계, 재생 기록 조회에 유리하다

### 단점

- 지연 시간이 RTSP보다 길다
- 초저지연 관제에는 불리할 수 있다
- 세그먼트 생성 과정이 필요하다

---

## 4. RTSP와 HLS.js의 핵심 차이

| 항목               | RTSP                             | HLS + HLS.js                                  |
| ------------------ | -------------------------------- | --------------------------------------------- |
| 정체               | 스트리밍 프로토콜                | HTTP 스트리밍 방식 + 브라우저 재생 라이브러리 |
| 주 사용 위치       | 카메라 ↔ 서버                    | 서버 ↔ 웹 브라우저                            |
| 브라우저 직접 재생 | 거의 불가                        | 가능                                          |
| 지연 시간          | 짧음                             | 상대적으로 김                                 |
| 장비 호환성        | IP 카메라와 매우 좋음            | 브라우저/웹 서비스와 매우 좋음                |
| 사용 목적          | 원본 수신, 관제, 녹화, 중계 입력 | 웹 재생, VOD/라이브 시청                      |

---

## 5. 우리 서비스 관점에서 어떻게 이해하면 좋은가?

현재 우리가 만들고 있는 드론 관제 시스템 같은 경우, 보통 역할 분리가 아래처럼 됩니다.

### 1. 카메라 -> 서버

이 구간은 `RTSP`가 적합합니다.

- 카메라 원본 스트림 수신
- 서버 저장
- 서버 측 AI 분석 또는 이벤트 처리
- 필요하면 다른 프로토콜로 변환

### 2. 서버 -> 프론트엔드

이 구간은 브라우저 환경을 고려해야 하므로 `HLS` 또는 `WebRTC`가 적합합니다.

- 브라우저에서 재생해야 함
- 프론트엔드는 `hls.js`로 `m3u8`를 붙여 재생 가능
- 단, 실시간성이 아주 중요하면 `WebRTC` 쪽이 더 적합할 수 있음

즉, 우리 서비스에서는 보통 이렇게 생각하면 됩니다.

- `RTSP`: 카메라 원본을 서버가 받는 용도
- `HLS.js`: 서버가 변환한 HLS 영상을 프론트가 보는 용도

---

## 6. 이번 프로젝트에서 왜 HLS를 선택하려고 하는가?

우리 프로젝트는 **브라우저 기반 드론 관제 시스템**을 만들고 있기 때문에,  
카메라 원본을 그대로 받는 것보다 **프론트엔드에서 안정적으로 재생할 수 있는 형태**가 더 중요합니다.

그래서 현재 구조에서는 `RTSP를 서버 입력으로 사용하고`,  
`프론트엔드 재생은 HLS + hls.js로 가져가는 방향`이 더 현실적입니다.

### 이유 1. 브라우저에서 바로 재생하기 쉽다

프론트엔드는 결국 웹 브라우저에서 돌아가야 합니다.

그런데 브라우저는 `rtsp://...` 주소를 직접 재생하지 못하므로,  
카메라 주소를 그대로 프론트에 붙이는 방식은 사용할 수 없습니다.

반면 HLS는 `m3u8` 기반의 HTTP 스트림이기 때문에 브라우저 환경과 훨씬 잘 맞습니다.

### 이유 2. 현재 서비스 구조가 웹 관제 화면에 가깝다

우리 서비스는 단순히 카메라 한 대를 보는 화면이 아니라 다음을 함께 보여줘야 합니다.

- 다중 카메라 모니터링
- 장치 상태 정보
- 로그 / 이벤트 정보
- 히스토리 영상 재생
- 향후 확장 가능한 관제 UI

이런 구조에서는 `브라우저에서 다루기 쉬운 스트림 방식`이 유리하고,  
그 기준에서 HLS가 프론트엔드와 잘 맞습니다.

### 이유 3. 히스토리 영상과도 연결하기 좋다

관제 시스템은 라이브만 중요한 것이 아니라,  
과거 영상을 다시 조회하고 재생하는 기능도 중요합니다.

HLS는 세그먼트 기반이라:

- 녹화 영상 관리
- 시간대별 재생
- 저장된 구간 재생
- HTTP 기반 다운로드/재생 흐름

같은 기능과 연결하기가 비교적 쉽습니다.

### 이유 4. 여러 카메라를 웹에서 운영하기에 안정적이다

RTSP는 실시간성은 좋지만 브라우저 친화적이지 않고,  
네트워크나 포트 이슈에도 민감할 수 있습니다.

반면 HLS는 HTTP 기반이어서:

- 프론트엔드 연동이 단순하고
- 인증/권한 처리 구조와 맞추기 쉽고
- 서버, 프록시, 배포 구조와 연결하기 쉽고
- 다중 사용자 재생 시 운영이 비교적 안정적입니다.

### 이유 5. 현재 단계에서 구현 난이도를 낮출 수 있다

지금 단계에서는 `초저지연 최적화`보다  
`브라우저에서 정상 재생되고, 여러 화면에 안정적으로 붙는 구조`를 먼저 확보하는 것이 더 중요합니다.

이 기준에서는 `RTSP -> 서버 -> HLS -> hls.js` 구조가  
프론트엔드 구현과 검증을 진행하기에 더 적절합니다.

### 정리

즉, 이번 프로젝트에서 HLS를 선택하려는 이유는  
**브라우저 호환성, 다중 카메라 관제 UI, 히스토리 영상 재생, HTTP 기반 운영 편의성** 때문입니다.

다만 이것이 `항상 HLS만 쓰면 된다`는 뜻은 아닙니다.

- 메인 관제 화면에서 초저지연이 정말 중요하면 `WebRTC`
- 웹 재생 안정성과 구현 편의성이 중요하면 `HLS`

처럼 화면 성격에 따라 혼합 구조를 고려할 수 있습니다.

## 7. 그럼 HLS와 WebRTC 중 무엇을 선택해야 하는가?

여기서 가장 헷갈리는 부분은  
`RTSP와 HLS의 차이`가 아니라, 실제 프론트엔드 재생 구간에서  
`HLS를 쓸지 WebRTC를 쓸지`를 어떻게 판단하느냐입니다.

결론부터 말하면 둘 중 하나가 절대적으로 더 좋다고 보기보다,  
**무엇을 우선할 것인지에 따라 선택이 갈립니다.**

### 핵심 차이

| 항목 | HLS | WebRTC |
| --- | --- | --- |
| 목적 | 웹 스트리밍 재생 | 초저지연 실시간 통신 |
| 전송 방식 | 세그먼트 기반 HTTP 스트리밍 | 실시간 P2P 또는 서버 중계 기반 |
| 지연 시간 | 비교적 큼 | 매우 짧음 |
| 브라우저 연동 | 비교적 단순 | 상대적으로 복잡 |
| 다중 카메라 운영 | 비교적 안정적 | 부하 관리가 더 어려울 수 있음 |
| 히스토리 영상과 연결 | 유리 | 상대적으로 불리 |
| PTZ, 조종, 즉각 반응 | 불리 | 유리 |

### 왜 HLS를 선택하는가?

HLS를 선택하는 이유는 보통 아래와 같습니다.

- 브라우저에서 안정적으로 재생해야 할 때
- 여러 카메라를 동시에 띄우는 화면이 필요할 때
- 히스토리 영상 재생과 자연스럽게 연결해야 할 때
- HTTP 기반으로 운영, 인증, 배포를 단순하게 가져가고 싶을 때
- 초저지연보다 **안정적인 웹 재생**이 더 중요할 때

즉, HLS는  
**"웹 관제 화면에 여러 영상을 안정적으로 붙여서 보여주는 것"**에 강합니다.

### 왜 WebRTC를 선택하는가?

WebRTC를 선택하는 이유는 보통 아래와 같습니다.

- 지연 시간을 최대한 줄여야 할 때
- 사용자의 조작에 영상 반응이 바로 따라와야 할 때
- 실시간성이 관제 품질의 핵심일 때
- 메인 카메라 하나를 집중해서 보는 화면이 중요할 때

즉, WebRTC는  
**"실시간 조작과 즉각적인 반응이 중요한 메인 라이브 화면"**에 강합니다.

### 우리 프로젝트 기준으로 보면?

우리 프로젝트는 현재 다음 성격이 더 강합니다.

- 웹 브라우저 기반 관제 시스템
- 다중 카메라 모니터링
- 장치 상태 / 이벤트 / 로그와 함께 보는 운영 화면
- 히스토리 영상 재생 기능도 중요함

이 기준만 놓고 보면 **기본 선택은 HLS가 더 자연스럽습니다.**

왜냐하면 지금 단계에서 더 중요한 것은:

- 브라우저에서 안정적으로 재생되는가
- 여러 화면에 붙였을 때 운영이 쉬운가
- 과거 영상 재생과 연결하기 쉬운가
- 프론트엔드 구현 복잡도를 낮출 수 있는가

이기 때문입니다.

### 그럼 WebRTC는 안 쓰는가?

그건 아닙니다.

만약 아래 조건이 강해지면 WebRTC를 선택하거나 혼합 구조를 고려할 수 있습니다.

- 메인 카메라 PTZ 제어 반응이 매우 중요함
- 드론 이착륙 순간을 거의 지연 없이 봐야 함
- 특정 운영 화면에서 초저지연이 핵심 요구사항이 됨

이 경우는 보통 이렇게 나눕니다.

- 메인 라이브 화면: `WebRTC`
- 서브 카메라 / 다중 타일 / 히스토리 영상: `HLS`

### 현재 문서 기준 판단

정리하면 현재 단계에서는 아래처럼 정리하는 것이 가장 명확합니다.

- **기본 선택:** `HLS`
- **선택 이유:** 웹 브라우저 호환성, 다중 카메라 운영, 히스토리 영상 재생, 구현 안정성
- **예외적으로 WebRTC를 고려하는 경우:** 메인 관제 화면에서 초저지연과 즉시 반응이 핵심일 때

즉, 지금 문서에서 `왜 HLS를 선택하는가?`에 대한 답은:

> 우리 프로젝트는 현재 **초저지연 단일 스트림 제어**보다  
> **브라우저 기반 다중 카메라 관제와 안정적인 재생 구조**가 더 중요하기 때문에 HLS를 우선적으로 고려한다.

반대로 `왜 WebRTC를 선택하는가?`에 대한 답은:

> 메인 라이브 화면에서 **지연 시간을 최소화해야 하는 강한 요구사항**이 있을 때 WebRTC를 선택한다.

## 8. HLS는 실제로 어떻게 동작하는가?

HLS는 영상을 하나의 큰 파일로 보내는 방식이 아니라,  
**작은 조각으로 나누어 순서대로 재생하는 방식**입니다.

기본 흐름은 아래와 같습니다.

```text
카메라 -> RTSP 원본 스트림 -> 서버
서버 -> 스트림을 잘게 자른 세그먼트(.ts 또는 fMP4) 생성
서버 -> 재생 목록 파일(.m3u8) 제공
브라우저(hls.js) -> m3u8을 읽고 세그먼트를 순서대로 요청
브라우저 -> 받은 조각을 이어 붙여 영상 재생
```

### 1. 카메라가 원본 스트림을 보낸다

카메라는 보통 `RTSP`로 원본 영상을 보냅니다.

이 단계에서 서버는:

- 카메라 스트림 수신
- 필요 시 녹화
- 필요 시 분석
- 필요 시 다른 포맷으로 변환

을 수행합니다.

### 2. 서버가 영상을 잘게 나눈다

HLS에서는 영상을 몇 초 단위의 작은 파일로 나눕니다.

예를 들면:

- `segment001.ts`
- `segment002.ts`
- `segment003.ts`

처럼 짧은 세그먼트들이 생깁니다.

이렇게 나누는 이유는:

- 네트워크가 끊겨도 일부만 다시 받기 쉽고
- 브라우저가 순차적으로 받아 재생하기 쉽고
- 라이브와 저장 영상 관리 모두에 유리하기 때문입니다.

### 3. 서버가 m3u8 재생 목록을 만든다

브라우저는 세그먼트 파일 이름을 미리 알 수 없기 때문에,  
서버는 어떤 세그먼트를 어떤 순서로 재생해야 하는지 적은 `m3u8` 파일을 함께 제공합니다.

이 파일은 쉽게 말하면:

- 현재 재생 가능한 조각 목록
- 각 조각의 길이
- 다음에 받아야 할 순서

를 알려주는 안내서 역할을 합니다.

### 4. 브라우저가 m3u8을 읽는다

프론트엔드에서는 `hls.js`가 먼저 `m3u8` 파일을 읽습니다.

그다음:

1. 어떤 세그먼트를 먼저 받아야 하는지 확인하고
2. 필요한 `.ts` 또는 `fMP4` 조각을 요청하고
3. `<video>` 태그에 붙여 재생합니다.

즉, `hls.js`는 HLS 스트림을 브라우저가 이해할 수 있도록 중간에서 처리하는 역할을 합니다.

### 5. 라이브 스트림은 목록이 계속 갱신된다

라이브 영상에서는 `m3u8` 파일이 한 번 만들어지고 끝나는 것이 아니라,  
새로운 세그먼트가 생길 때마다 계속 갱신됩니다.

브라우저는 이 목록을 주기적으로 다시 읽으면서:

- 새 조각이 생겼는지 확인하고
- 새 영상 데이터를 받아오고
- 현재 재생 위치 뒤에 이어 붙입니다.

그래서 HLS 라이브는 `계속 추가되는 짧은 영상 조각을 따라가는 방식`으로 동작합니다.

### 6. 그래서 지연이 생긴다

HLS는 세그먼트를 만들고, 목록을 갱신하고, 브라우저가 다시 읽는 과정이 있기 때문에  
RTSP나 WebRTC보다 지연이 더 생깁니다.

즉:

- 장점: 브라우저 친화적이고 안정적
- 단점: 초저지연에는 불리함

이라는 특성이 자연스럽게 따라옵니다.

---

## 9. 언제 어떤 걸 쓰는 게 좋은가?

### RTSP가 더 적합한 경우

- 카메라 원본 스트림을 받아와야 할 때
- 지연 시간을 최대한 줄여야 할 때
- 서버에서 녹화, 분석, 재분배를 해야 할 때
- CCTV, NVR, VMS 같은 장비 중심 환경일 때

### HLS.js가 더 적합한 경우

- 웹 브라우저에서 영상을 바로 재생해야 할 때
- 프론트엔드 구현 난이도를 낮추고 싶을 때
- 라이브뿐 아니라 재생 영상(VOD, 히스토리 영상)도 함께 다뤄야 할 때
- HTTP 기반 인프라와 자연스럽게 연결하고 싶을 때

## 10. 장단점 요약

### RTSP

#### 장점

- 저지연
- 카메라 장비 호환성 우수
- 서버 입력 스트림으로 적합

#### 단점

- 브라우저 직접 재생 어려움
- 프론트엔드에서 바로 쓰기 곤란
- 네트워크 설정 이슈 가능

### HLS.js

#### 장점

- 웹 재생에 적합
- 프론트엔드 구현이 비교적 단순
- HTTP 기반이라 배포와 운영이 쉬움

#### 단점

- 지연이 상대적으로 큼
- 실시간 관제에서는 답답할 수 있음
- HLS 변환 파이프라인이 필요

---

## 11. 최종 정리

정리하면, `RTSP`는 **카메라와 서버 사이의 원본 스트림 수신용 기술**에 가깝고, `hls.js`는 **서버가 변환해 준 HLS 영상을 브라우저에서 재생하는 도구**에 가깝습니다.

따라서 둘 중 하나만 선택하는 문제라기보다, 보통은 아래처럼 함께 사용합니다.

```text
RTSP: 카메라 -> 서버
HLS.js: 서버 -> 브라우저
```

만약 실시간성이 아주 중요한 메인 관제 화면이라면 `RTSP -> WebRTC`,  
웹 호환성과 구현 편의성이 중요한 화면이라면 `RTSP -> HLS -> hls.js` 구조를 고려하는 것이 일반적입니다.
