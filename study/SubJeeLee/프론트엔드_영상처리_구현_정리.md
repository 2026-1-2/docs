# 프론트엔드 영상 처리 구현 정리

## 1. 먼저 결론부터

프론트엔드에서 해야 하는 일은 **카메라 원본 영상을 직접 처리하는 것**이 아니라,  
**서버가 가공해서 넘겨준 스트림을 안정적으로 재생하고, 상태를 관리하고, 관제 UI와 연결하는 것**입니다.

즉 역할을 구분하면 아래와 같습니다.

```text
카메라 -> 서버 -> 프론트엔드
```

- **카메라**
  - RTSP 원본 스트림 제공
- **서버**
  - RTSP 수신
  - 필요 시 HLS/WebRTC로 변환
  - 녹화, 분석, 인증, 접근 제어 담당
- **프론트엔드**
  - 변환된 스트림 재생
  - 재생 상태 관리
  - 에러 처리 및 재연결
  - 다중 카메라 UI 구성
  - 이벤트, 센서 데이터, PTZ UI와 연동

따라서 프론트엔드에서의 "영상 처리"는 보통 다음 의미에 가깝습니다.

- 스트림 재생
- 플레이어 생명주기 관리
- 다중 영상 배치
- 저하 없는 렌더링 최적화
- 재연결 및 fallback 처리
- 실시간 데이터와의 UI 통합

---

## 2. 프론트엔드가 RTSP를 직접 다루면 안 되는 이유

웹 브라우저는 `rtsp://...` 주소를 일반적으로 직접 재생하지 못합니다.

그래서 프론트엔드는 보통 아래 형태 중 하나를 받습니다.

- `HLS (.m3u8)` 스트림
- `WebRTC` 스트림
- 녹화 영상용 `MP4`

즉 프론트엔드가 직접 RTSP를 붙잡고 디코딩하는 구조가 아니라,  
서버가 브라우저 친화적인 형태로 바꿔 준 결과물을 재생하는 구조가 일반적입니다.

---

## 3. 프론트엔드 구현에서 가장 먼저 정해야 하는 것

### 1. 라이브 영상의 우선순위

- **초저지연이 핵심**이면 `WebRTC`
- **브라우저 호환성과 구현 단순성**이 중요하면 `HLS + hls.js`

### 2. 화면 종류

- 메인 실시간 관제 화면
- 다중 카메라 썸네일 화면
- 과거 영상 재생 화면
- 장치 상세 화면

보통 화면마다 같은 방식을 쓸 필요는 없습니다.

예를 들면:

- 메인 카메라: `WebRTC`
- 서브 카메라: `HLS`
- 과거 영상: `MP4` 또는 `HLS`

## 4. HLS.js 기준 프론트엔드 구현 방식

React 기준으로 가장 일반적인 구조는 다음과 같습니다.

### 기본 흐름

1. 서버에서 `m3u8` URL을 받는다
2. `<video>` 태그를 만든다
3. `hls.js` 인스턴스를 생성한다
4. `hls.loadSource()`로 HLS 주소를 넣는다
5. `hls.attachMedia(video)`로 비디오와 연결한다
6. 언마운트 시 `destroy()`로 정리한다

### 예시 코드

```tsx
import { useEffect, useRef } from 'react';
import Hls from 'hls.js';

interface HlsPlayerProps {
  src: string;
  autoPlay?: boolean;
  muted?: boolean;
}

export default function HlsPlayer({
  src,
  autoPlay = true,
  muted = true,
}: HlsPlayerProps) {
  const videoRef = useRef<HTMLVideoElement | null>(null);

  useEffect(() => {
    const video = videoRef.current;
    if (!video || !src) return;

    if (video.canPlayType('application/vnd.apple.mpegurl')) {
      video.src = src;
      return;
    }

    if (!Hls.isSupported()) return;

    const hls = new Hls({
      enableWorker: true,
      lowLatencyMode: true,
    });

    hls.loadSource(src);
    hls.attachMedia(video);

    hls.on(Hls.Events.ERROR, (_, data) => {
      if (data.fatal) {
        switch (data.type) {
          case Hls.ErrorTypes.NETWORK_ERROR:
            hls.startLoad();
            break;
          case Hls.ErrorTypes.MEDIA_ERROR:
            hls.recoverMediaError();
            break;
          default:
            hls.destroy();
        }
      }
    });

    return () => {
      hls.destroy();
    };
  }, [src]);

  return (
    <video
      ref={videoRef}
      autoPlay={autoPlay}
      muted={muted}
      playsInline
      controls={false}
      className="w-full h-full object-cover"
    />
  );
}
```

## 5. 프론트엔드에서 중요한 생명주기 관리 포인트

### 1. 컴포넌트가 사라질 때 반드시 정리해야 한다

영상 플레이어는 일반 UI 컴포넌트보다 무겁습니다.

정리하지 않으면:

- 메모리 누수
- 네트워크 연결 유지
- 백그라운드 디코딩 지속
- 탭이 많아질수록 성능 저하

따라서:

- `hls.destroy()`
- `video.pause()`
- 필요 시 `video.src = ''`

같은 정리를 명확히 해야 합니다.

### 2. 숨겨진 탭/비활성 패널은 재생을 줄여야 한다

관제 시스템은 여러 카메라를 한 번에 띄우기 때문에,  
보이지 않는 패널까지 전부 풀 해상도로 계속 재생하면 브라우저가 버티지 못할 수 있습니다.

그래서 보통:

- 비활성 패널은 정지
- 작은 썸네일은 저화질 스트림 사용
- 메인 카메라만 고화질 유지

전략을 함께 가져갑니다.

## 6. 다중 카메라 관제 화면에서의 최적화 전략

이 부분이 우리 서비스에서 가장 중요합니다.

### 1. 모든 카메라를 같은 품질로 재생하지 않는다

예:

- 메인 피드: 1080p 또는 고화질
- 서브 피드: 360p ~ 720p
- 미리보기 피드: 더 낮은 비트레이트

### 2. 메인 피드와 서브 피드를 분리한다

메인 피드는 사용자가 집중해서 보는 화면이고,  
서브 피드는 상황 감시용이므로 우선순위를 다르게 둬야 합니다.

즉:

- 메인 피드: 낮은 지연, 높은 품질
- 서브 피드: 많은 수를 동시에 띄우되 CPU/GPU 부담 최소화

### 3. 화면에 없는 스트림은 끈다

탭, 패널, 드롭다운, 모달처럼 현재 안 보이는 영역의 스트림은 적극적으로 정지하는 것이 좋습니다.

### 4. 이벤트 기반 확대를 고려한다

예를 들어 서브 카메라 타일을 클릭하면:

1. 메인 피드 영역에 승격
2. 고화질 스트림으로 교체
3. 나머지 피드는 저화질 유지

이런 방식이 대형 모니터 관제 UX에도 잘 맞습니다.

## 7. 프론트엔드에서 "영상 분석"까지 하면 안 되는 이유

프론트엔드에서 OpenCV처럼 무거운 프레임 분석을 직접 돌리는 것은 일반 관제 웹앱에서는 권장되지 않습니다.

이유는 다음과 같습니다.

- 브라우저 CPU/GPU 부담이 커짐
- 다중 카메라에서 성능 저하가 심함
- 사용자 디바이스 성능 편차가 큼
- 보안과 접근 제어가 어려워짐

따라서 실제 분석은 보통 서버에서 합니다.

예:

- 객체 탐지
- 이상 이벤트 감지
- 풍속/기상 기반 알림 판단
- 녹화 구간 태깅

프론트엔드는 그 결과만 받아서 보여주는 쪽이 적절합니다.

## 8. 프론트엔드에서 해야 하는 부가 기능

### 1. 재생 상태 시각화

플레이어는 단순히 영상만 나오면 끝이 아닙니다.

관제 화면에서는 다음 상태를 함께 표현해야 합니다.

- 연결 중
- LIVE
- 지연 증가
- 신호 약함
- 재연결 중
- 연결 끊김

### 2. 스트림 메타데이터 표시

- 해상도
- 비트레이트
- 지연 시간
- 프로토콜
- 카메라 이름
- 장치 상태

이 정보는 운영자가 문제를 빨리 파악하는 데 중요합니다.

### 3. 이벤트와 동기화

예:

- 특정 시간대 이벤트 클릭
- 해당 시점 녹화 영상으로 이동
- 카메라 타일 강조
- 알림 배지 출력

즉 영상 플레이어는 단독 컴포넌트가 아니라,  
관제 대시보드 전체 상태와 연결된 UI여야 합니다.

## 9. 우리 프로젝트에 맞는 구현 방향

현재 MMP 드론 관제 시스템 관점에서는 아래처럼 가져가는 것이 현실적입니다.

### 1. 라이브 관제

- 카메라 -> 서버: `RTSP`
- 서버 -> 프론트:
  - 메인 화면은 `WebRTC` 우선 검토
  - 서브 화면은 `HLS + hls.js` 또는 저화질 스트림

### 2. 히스토리 재생

- `HLS` 또는 `MP4`
- 브라우저 기본 플레이어나 `hls.js` 사용

### 3. 프론트엔드 컴포넌트 구조

- `CameraPlayer`
  - 실제 재생 담당
- `CameraTile`
  - 플레이어 + 상태 배지 + 메타데이터
- `MainCameraPanel`
  - 메인 스트림 집중 영역
- `SubCameraGrid`
  - 다중 피드 배치
- `PlaybackPlayer`
  - 과거 영상 재생 전용

## 10. 구현 시 주의사항

### 1. 인증 정보를 프론트에 직접 두지 않는다

`rtsp://id:password@...` 같은 원본 주소를 프론트에 그대로 넣으면 안 됩니다.

프론트는 반드시 서버가 발급한 안전한 재생 URL만 받아야 합니다.

### 2. 자동 재생 정책을 고려해야 한다

브라우저는 소리 있는 자동 재생을 막는 경우가 많습니다.

그래서 라이브 썸네일은 보통:

- `muted`
- `playsInline`
- `autoPlay`

조합으로 시작합니다.

### 3. 해상도보다 안정성이 먼저다

관제 시스템에서는 아주 선명한 한 장면보다,  
여러 피드가 끊기지 않고 안정적으로 동시에 보이는 것이 더 중요할 수 있습니다.

### 4. 플레이어 수를 과도하게 늘리지 않는다

카메라 수가 많아질수록 브라우저 성능 한계가 빨리 옵니다.

따라서:

- 한 화면 최대 동시 재생 수 제한
- 페이지네이션 또는 가상화
- 메인/서브 우선순위 분리

같은 설계가 필요합니다.

---

## 11. 최종 정리

프론트엔드에서의 영상 처리는 **RTSP 원본을 직접 다루는 것**이 아니라,  
**서버가 변환한 HLS/WebRTC 스트림을 브라우저에서 안정적으로 재생하고 관리하는 것**입니다.

정리하면 역할은 아래와 같습니다.

- `RTSP`: 카메라 원본 수신용
- `HLS.js`: 브라우저 HLS 재생용
- `프론트엔드 구현 포인트`: 재생, 상태 관리, 에러 복구, 다중 카메라 최적화, 관제 UI 통합

즉 우리 서비스의 핵심은 "프론트에서 무거운 영상 분석을 직접 한다"가 아니라,  
"프론트에서 여러 영상과 관제 상태를 안정적으로 통합해 보여준다"에 더 가깝다고 볼 수 있습니다.
