# 디자인 시스템, 컴포넌트 모음집이 아니었나요?

**부제: 프론트엔드 개발자 관점에서 다시 그리는 디자인 시스템**

프론트엔드 개발을 하다 보면 누구나 한 번쯤 이런 순간을 마주합니다.

> _"어? 이 버튼 저번 페이지에서 만든 거랑 똑같은데 색상만 조금 다르네? 일단 `className` 추가해서 덮어씌워야겠다."_

> _"이 데이터 테이블, 저쪽 메뉴에서도 써야 하는데 데이터 구조가 달라서 재사용이 안 되네. 그냥 하나 더 만들자."_

처음에는 별문제가 아닙니다.

하지만 프로젝트가 커지고 복잡한 대시보드를 구축하기 시작하면, 어느새 프로젝트 폴더 안에는 `Button_v2`, `Button_final`, `Real_Final_Table` 같은 컴포넌트들이 증식하기 시작합니다.

버튼의 패딩 값 4px을 수정하기 위해 수십 개의 파일을 뒤져야 하는 '유지보수의 늪'. 저 역시 이번 관제 시스템 프로젝트를 시작하며 이 늪에 빠질 뻔했습니다. 그리고 이를 해결하기 위해 **디자인 시스템(Design System)** 이라는 개념을 다시 들여다보기 시작했습니다.

<br/>

## 오해 1. 디자인 시스템은 디자이너의 영역 아닌가요?

저 역시 처음에는 '디자인 시스템 = 예쁜 피그마(Figma) 파일' 혹은 'HEX 색상 코드 모음집'이라고 생각했습니다.

하지만 프론트엔드 개발자에게 디자인 시스템은 단순한 **'시각적 가이드라인(Style Guide)'** 을 넘어섭니다.

그것은 제품을 만드는 구성원 모두가 합의한 **'단일 진실 공급원(Single Source of Truth)'** 이자, 화면을 조립하는 **'공통 언어'** 입니다.

"거기 버튼 파란색으로 해주세요"라는 모호한 요청 대신, "여기 상태 배지는 `Semantic-Warning` 토큰을, 버튼은 `Primary-500` 토큰을 사용해 주세요" 라는 명확한 커뮤니케이션이 가능해집니다.

<br/>

## 오해 2. 빡빡한 규칙 때문에 개발자의 자유도가 떨어지지 않나요?

> "모든 걸 컴포넌트화하고 규칙에 맞추면, 프론트엔드 개발자가 화면을 유연하게 그릴 수 없지 않나요?"

역설적이게도, **잘 구축된 디자인 시스템은 개발자에게 진정한 의미의 '자유'를 줍니다.**

생각해 보세요. 매번 버튼의 모서리 둥글기(border-radius)가 4px인지 8px인지, 에러 메시지 폰트 크기가 12px인지 14px인지 고민하는 것이 우리가 진짜 해야 할 중요한 고민일까요?

디자인 시스템이 이런 소모적인 의사결정을 대신해 주면, 프론트엔드 개발자는 비로소 **진짜 중요한 엔지니어링 문제**에 집중할 수 있게 됩니다.

무거운 실시간 CCTV 영상을 어떻게 지연 없이 렌더링할 것인지, 초당 갱신되는 센서 데이터의 리렌더링 최적화는 어떻게 할 것인지와 같은 복잡한 아키텍처 로직 말입니다.

<br/>

## 프론트엔드 아키텍처로서의 디자인 시스템

그렇다면 프론트엔드 개발자는 이 시스템을 코드 레벨에서 어떻게 '설계'해야 할까요? 단순히 UI 껍데기만 만드는 것이 아니라, 동료 개발자가 가져다 쓰기 편하면서도 통제 가능한 구조를 고민해야 합니다.

이번 프로젝트를 준비하며, 컴포넌트의 역할과 복잡도에 따라 두 가지 패턴을 어떻게 적용할 수 있을지 정리해 보았습니다.

### **1. 원자 단위의 확고한 통제: Flat Component**

가장 작은 단위(Atom)인 `Button`, `Badge` 같은 컴포넌트들은 단일 책임 원칙(SRP)을 지키며 설계됩니다. 여기서 핵심은 **'자유도를 뺏는 것'** 입니다.

디자인 시스템이 무너지는 가장 큰 이유는 Flat Component에 너무 많은 자유도(Props)를 열어두었을 때 발생합니다.

**❌ 나쁜 예 (과도한 자유도)**

```tsx
// 동료 개발자가 마음대로 픽셀과 색상을 조작할 수 있음 -> 파편화의 시작
<Button
  bgColor="#12A5B5"
  textColor="white"
  borderRadius="8px"
  padding="10px 20px"
>
  저장하기
</Button>
```

**✅ 좋은 예 (디자인 토큰 기반의 통제)**

```tsx
// 시스템이 정의한 variant와 size만 허용 -> 완벽한 시각적 일관성
<Button variant="primary" size="md">
  저장하기
</Button>
```

#### **장점:**

- 사용하는 개발자는 디자인 고민(여백, 색상 등)을 전혀 할 필요가 없습니다

- 시스템 전반에 걸쳐 `variant="danger"`는 항상 동일한 빨간색
  (`Semantic-Error`)과 동일한 호버 애니메이션을 보장합니다.

#### **단점(Trade-off):**

- 마케팅 이벤트 페이지처럼 일회성으로 완전히 독특한 스타일(예: 네온 핑크색 버튼)이 필요할 때는 유연하게 대처하기 어렵습니다.

- 하지만 관제 대시보드와 같은 B2B 시스템에서는 이러한 '엄격함'이 오히려 유지보수성을 극대화하는 강력한 장점이 됩니다.

### **2. 레이아웃의 자유도를 극대화: Compound Component**

반면, `DataTable`이나 복잡한 `Card`처럼 유기체(Organism) 수준의 컴포넌트들은 상황이 다릅니다.

모든 경우의 수를 Props로 뚫어주다 보면 `isOpen`, `hasHeader`, `showFooter`, `customClassNameForTitle` 등 끝없는 Props Drilling 지옥에 빠지게 됩니다.

이를 해결하기 위해 자식 컴포넌트들을 퍼즐처럼 조립해 쓰는 **Compound Component 패턴**을 채택했습니다.

```tsx
// 직관적이고 선언적인 데이터 테이블 조립
<Table>
  <Table.Header>
    <Table.Column>시간</Table.Column>
    <Table.Column>상태</Table.Column>
  </Table.Header>
  <Table.Body>
    {data.map((log) => (
      <Table.Row key={log.id}>
        <Table.Cell>{log.time}</Table.Cell>
        <Table.Cell>
          <StatusBadge type={log.status} />
        </Table.Cell>
      </Table.Row>
    ))}
  </Table.Body>
</Table>
```

#### 작동 원리: 부모 컴포넌트(<Table>)가 내부 상태를 Context API로 관리합니다.

#### 장점:

- 사용하는 동료 개발자는 JSX 구조만 봐도 UI의 계층을 직관적으로 이해할 수 있습니다.

- 페이지에 따라 헤더에 필터를 추가하든, 셀 안에 새로운 배지를 넣든 테이블 내부 코드를 뜯어고칠 필요 없이 블록만 갈아 끼우면 됩니다.
- Flat Component에서 제한했던 '레이아웃의 자유도'를 여기서 선언적으로 풀어주는 것입니다.

## MMP 서비스에 적용하기 전, 방향을 정리해 보기

> 이론적인 고민을 바탕으로, 이번 **'MMP 버티포트 CCTV 모니터링 시스템'** 프로젝트에 디자인 시스템을 반영한다면 어떤 방향으로 설계하는 것이 적절할지 학습하며 정리해 보았습니다.

관제 시스템 특성상 24시간 화면을 주시해야 하므로 눈의 피로도를 낮추는 **다크 모드(Dark Mode)** 를 기본 방향으로 고려했습니다.

여기에 MMP 기업 로고에서 추출한 청록색(Primary)과 라임그린(Secondary)을 포인트 컬러 토큰으로 삼아 브랜드 아이덴티티를 녹여낼 수 있겠다고 판단했습니다.

### **1. Design Token과 Tailwind CSS의 결합**

피그마에서 정의한 컬러, 타이포그래피, Spacing 스케일은 모두 `tailwind.config.ts`에 토큰(Token)으로 주입하는 방식이 적절하다고 보았습니다.

개발 시에는 헥스 코드(`#12A5B5`)를 직접 입력하는 대신, `text-primary-500`이나 `bg-semantic-error`처럼 의미를 부여한 토큰만을 사용해야 디자인과 코드의 일관성을 유지할 수 있다고 정리했습니다.

### **2. 관제 도메인에 특화된 컴포넌트 설계**

- **Flat Pattern 적용:**
  드론 기체의 비행 안전과 직결되는 풍속/전파 경고나, 카메라 스트리밍 방식(WebRTC/HLS)을 나타내는 `StatusBadge` 컴포넌트는 단일 책임 원칙에 따라 철저하게 시각적 일관성을 통제하는 방식이 적합하다고 보았습니다.

- **Compound Pattern 적용:** `EventLogTable`이나 `HardwareStatusCard`처럼 실시간으로 갱신되는 복잡한 데이터들은 Compound 패턴으로 조립해 두면, 추후 요구사항이 변경되더라도 내부 로직 파편화 없이 유연하게 레이아웃을 대응할 수 있겠다고 판단했습니다.

## 💡 학습하며 정리한 인사이트

이번 주제를 학습하며, 디자인 시스템을 실제 서비스에 반영하기 전에 프론트엔드 개발자로서 미리 정리해 둘 필요가 있다고 느낀 포인트는 다음과 같습니다.

### **첫째, 초기 세팅에는 시간을 아끼지 말자.**

프로젝트 초기에는 '당장 기능 개발하기도 바쁜데 폰트 스케일이랑 컬러 토큰을 먼저 정의하는 것이 맞을까?'라는 의문이 들 수 있습니다. 하지만 관련 사례들을 살펴보면, 컴포넌트와 토큰이 쌓일수록 이후 화면 조립 속도가 크게 빨라진다는 점을 확인할 수 있었습니다.

### **둘째, UI 고민이 사라지니 '진짜 기술적인' 문제에 집중할 수 있었습니다.**

버티포트 관제 시스템은 끊임없이 들어오는 무거운 24시간 영상 피드와, 초당 갱신되는 외부 API(기상, 전파 등) 데이터를 한 화면에서 처리해야 하는 서비스입니다.
따라서 매번 CSS 픽셀을 맞추고 상태에 따른 조건부 렌더링 코드를 반복하기보다, **'어떻게 하면 비디오 렌더링 병목을 줄일 수 있을까?', 'Zustand를 활용해 어떻게 상태 갱신에 따른 불필요한 리렌더링을 방지할까?'** 와 같은 깊이 있는 엔지니어링 문제에 집중할 수 있는 구조를 미리 마련하는 것이 중요하다고 정리했습니다.

### **셋째, 개발자는 '코더(Coder)'가 아닌 '아키텍트(Architect)'가 되어야 합니다.**

단순히 주어진 피그마 화면을 브라우저에 똑같이 그려내는 것은 코딩입니다. 하지만 서비스의 확장성을 고려하여 규칙을 세우고, 동료가 사용하기 편한 컴포넌트 구조를 '설계'하는 것은 엔지니어링입니다.

정리하자면, 이 단계에서는 디자인 시스템을 실제 서비스에 반영하기 전에 어떤 기준과 구조로 접근해야 할지를 학습하고 설계 관점에서 정리하는 데 의미가 있었습니다.

다음 섹션에서는 이러한 고민을 바탕으로, 디자인 시스템을 실제 MMP 서비스에 어떤 방식으로 반영했는지 구체적으로 이어서 정리해 보겠습니다.
