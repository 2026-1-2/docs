    - 백엔드는 카메라 관리와 카메라 스트리밍 기능 구현 진행

    - 서버 설치 장소가 확정되지 않아 실제 운영 환경 구성이 어려운 문제 확인
    - 서버가 정상적으로 켜지지 않았던 문제와 현장 네트워크 연결을 위한 랜선 제작 과정 공유
    - 브라우저에서 HLS 영상을 재생할 때 약 30초의 영상 지연이 발생하는 문제 확인
- **결정 사항**:
    - 서버와 네트워크 문제를 발표자료의 이슈 사항 및 해결 과정에 포함
    - 영상 지연은 HLS segment 생성, playlist 갱신 및 브라우저 버퍼링 관점에서 원인 분석

### 📎 안건 4: 서버 및 미디어 처리 아키텍처 검토
- **논의 내용**:
    - 현재 Recorder(MediaMTX)는 카메라 RTSP에 직접 접속하여 24시간 녹화를 담당
    - NestJS도 카메라 RTSP에 별도로 접속하여 HLS 변환 후 브라우저에 라이브 스트림 제공
    - 현재 구조에서는 카메라 1대당 RTSP 커넥션이 2개 생성됨
    - Recorder 장애 시 라이브 스트림 유지, NestJS 재시작 시 녹화 유지를 위한 장애 격리 목적으로 기능을 분리함
    - 다중 RTSP 연결로 인한 카메라 부하, 네트워크 대역폭 증가 및 장치별 연결 제한 가능성 논의
    - 단일 서버에서 Media Server와 API Server를 함께 운영할 경우 CPU, 메모리 및 네트워크 자원 경합 가능성 검토
    - Media, Backend API, PTZ Control, Video Recorder 기능의 분리 범위 논의
- **결정 사항**:
    - 장애 격리 목적은 유지하되 카메라 RTSP 스트림을 중복 수신하지 않는 구조를 우선 검토
    - MediaMTX가 RTSP 스트림을 한 번 수신하고 녹화, 라이브 스트리밍 및 WebRTC 송출 기능이 이를 공유하는 방향 검토
    - 카메라 수 증가와 실제 현장 도입을 고려하여 서비스별 분리 가능한 구조로 설계
- **추가 작업**:
    - 단일 서버 운영 시 장애 및 자원 경합 시나리오 정리
    - Media Server, API Server, PTZ Control 및 Recorder 분리 구조도 작성
    - WebRTC 전환 가능성 및 네트워크 포트 구성 확인
- **담당자**: 백엔드 및 인프라 담당
- **기한**: 아키텍처 확정 전까지
